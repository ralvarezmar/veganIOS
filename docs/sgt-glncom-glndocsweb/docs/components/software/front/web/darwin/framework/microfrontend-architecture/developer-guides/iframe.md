# Iframe

![Getting started with microfront development](../../../../../assets/images/darwin/iframe.png){ style="display: block; margin: 0 auto; width:75%" }

!!! warning
    **From Darwin Architecture we strongly discourage the use of iframes. The following documentation tries to bring some support to it but also exposes the problems**.

!!! note
    **If you want to integrate a Microfront into a Shell with the recommended approach, follow this documentation**: [How to integrate a Microfront into a Shell application](./how-to-integrate-a-microfront-into-a-shell-application/index.md).

Using Darwin's architecture with iFrame, with the approach that the shell is responsible for initializing security (for generating and refreshing the token), and the Microfronts are the ones consuming that token, we encounter an issue that is not present in the federated modules solution: the shell and the microfront do not share session storage, which means the token generated in the shell is not available in the Microfront embedded through the iFrame. <!-- markdownlint-disable MD013 -->

The solution for this problem is the inclusion of a light shell, called **ShellLite**, that initializes the security before the Microfront app is initialized. This implies that we need to bootstrap this light shell before bootstrapping the Microfront app itself. Let's look at it in detail.

## How to setup the configuration in order to integrate a Microfront through a Iframe

### Bootstrap setup

When a Microfront is consumed through federated modules, the Security is initialized by the Shell, allowing the Microfront to use the token generated by the Shell.
However, when a Microfront is consumed through an `iframe`, due to the constraints that arise, it is necessary to use a `ShellLite` within the iframe. This `ShellLite` contains the Security, enabling the Microfront to consume it.

Therefore, there must be two ways to launch a Microfront depending on how it is consumed, and that's why there are two bootstrap files, `bootstrap-mfe.ts` and `bootstrap-shell-lite.ts`.
The first one is exposed by Webpack to be invoked as a federated module, while the second one is only invoked from the `index.html`.

In turn, the `bootstrap-shell-lite.ts` is responsible for initializing the `ShellLite` and the Security and must also internally incorporate the Microfront, specifically in its template.

```ts
bootstrapShell(ShellLite, shellLiteConfig)
  .catch(err => console.error(err));;
```

The key is the Microfront will be invoked from the `ShellLite` once the Security has been initialized.

### ShellLite

The `ShellLite` Angular component will be initialized in the `index.html`. This component will be in charge of invoking the Microfront:

```ts
/**
 * ShellLite
 */
@Component({
  ...
  selector: 'app-key-sl',
  template: `
    <h1>ShellLite</h1>
    @if(isLoaded()){
      <microfront-tag [mountPath]="mountPath" />
    }
  `,
})
export class ShellLite extends MicrofrontContainerDirective implements OnInit {
  ...
}
```

The `index.html` of the Microfront:

```html
<app-key-sl></app-key-sl>
```

When initializing Security, we have two options: either through the `provideConfig` or by directly setting the minimum options of the Security.

The `technical-grouping` we recommend using is the same as the Microfront, adding the suffix `sl`:

- Microfront: `f-ng-00000000-archetype-wmf-mcf`
- ShellLite of the Microfront: `f-ng-00000000-archetype-wmf-mcf-sl` (please note the suffix)

#### Using dynamic config

The library has to be imported in the `shell-lite.config.ts` specifying the technical-grouping:

```ts
provideConfig({
  technicalGrouping: 'f-ng-00000000-archetype-wmf-mcf-sl'
})
```

Additionally, you will need to configure Nginx by adding the necessary rules so that the Microfront can separately obtain both `config.json` files, which will differ depending on whether we are working with local Nginx or in an environment deployed on OpenShift.

- Configuration for local Nginx

    ``` text
    # Shell-lite: request to config properties
    location ~ ^/(en-US|es)/mf-ng-00000000-archetype-wmf-mcf-sl/config.json {
      rewrite ^/(en-US|es)/mf-ng-00000000-archetype-wmf-mcf-sl/config.json /shell-lite/config.json break;
      proxy_pass http://localhost:3001;
    }
    ```

    ``` text
    # Microfront: request to config properties
    location ~ ^/(en-US|es)/mf-ng-00000000-archetype-wmf-mcf/config.json {
      rewrite ^/(en-US|es)/mf-ng-00000000-archetype-wmf-mcf/config.json /config.json break;
      proxy_pass http://localhost:3001;
    }
    ```

- Configuration for deployed Nginx

    ``` text
    <% if ENV["CONFIG_END_POINT"] %>
      # to get shell-lite config properties
      location ~ ^<%= ENV["relativePath"] %>/(en-US|es)/mf-ng-00000000-archetype-wmf-mcf-sl/config.json {
        rewrite ^<%= ENV["relativePath"] %>/(en-US|es)/mf-ng-00000000-archetype-wmf-mcf-sl/config.json /mf-ng-00000000-archetype-wmf-mcf-sl/dev/master/mf-ng-00000000-archetype-wmf-mcf-sl.json break;
        proxy_pass <%= ENV["CONFIG_END_POINT"] %>;
      }

      # to get mcf config properties
      location ~ ^<%= ENV["relativePath"] %>/(en-US|es)/mf-ng-00000000-archetype-wmf-mcf/config.json {
        rewrite ^<%= ENV["relativePath"] %>/(en-US|es)/mf-ng-00000000-archetype-wmf-mcf/config.json /f-ng-00000000-key-mcf-ng13/dev/master/mf-ng-00000000-archetype-wmf-mcf.json break;
        proxy_pass <%= ENV["CONFIG_END_POINT"] %>;
      }
    <% end %>
    ```

- Configuration for local development

    Have to be added in the file `proxy.conf.json`

    ``` json
    "/mf-ng-00000000-archetype-wmf-mcf-sl/config": {
      "target": "http://localhost:3001",
      "pathRewrite": {
        "^/mf-ng-00000000-archetype-wmf-mcf-sl": "shell-lite"
      }
    },
    "/mf-ng-00000000-archetype-wmf-mcf/config": {
      "target": "http://localhost:3001",
      "pathRewrite": {
        "^/mf-ng-00000000-archetype-wmf-mcf": ""
      }
    }
    ```

#### Using static config

The library has to be imported in the `shell-lite.config.ts` with this minimal configuration:

``` ts
provideSecurity(
  withStaticConfig({
    appKey: 'appKey',
    appName: 'appName',
    technicalGrouping: 'mf-ng-00000000-archetype-wmf-mcf-sl',
    endpoint: 'http://localhost:3001/api/security/tokens',
    reminderTime: 32000,
    tkinss: true
  }),
),
```

### Advantages and disadvantages using dynamic or static config

The main difference between both solutions is that if you directly use the static config, the solution is simpler to implement, but the configuration must be in the code. This has two direct consequences:

1. To make a change in the configuration, you will have to make a change in the code and propagate the change through the pipeline.
2. You cannot have different configurations per environment. Therefore, the solution using two `config.json` files is a bit more complex but offers greater flexibility.

### Iframe invocation

#### `token`

The security module, in one of its steps, tries to obtain the token from the query params. The Microfront can take advantage of this to initialize security. To do this, you simply get the stored token.

``` ts
//component typescript that will invoke the iframe
securityService: SecurityService = inject(SecurityService);
token = securityService.token;
```

#### language

As the Microfront must use the Angular standard i18n, the language must also be added in the URL of the `iFrame`.

!!! note
    If the Shell application are using the standard Angular i18n, then the language of the application can be obtained through the localeId token.
    For more information visit [Internationalization and Location](./internationalization-and-location.md).

``` ts
//component typescript that will invoke the iframe
localeId: string = inject(LOCALE_ID);
```

!!! warning
    This param is mandatory for the Microfront.

#### `dw-channel`

The current channel can be informed through the param `dw-channel`. It can be retrieve through:

``` ts
//component typescript that will invoke the iframe
securityService: SecurityService = inject(SecurityService);
channel= securityService.channel;
```

#### Example invocation

In the component that invokes the iframe, the token, language and channel can be retrieved as explained before and used in the html in this way:

``` html
<!-- component html that will invoke the iframe -->

<iframe
  src="https://dominio-microfront/{{localeId}}/?token={{token}}&dw-channel={{channel}}"
  height="800"
  width="800"
></iframe>
```

## Why you should not use an iframe as the solution

### Disadvantages of using iframes

!!! warning
    This is a solution for legacy or unsupported applications.

- **Strict Isolation**: iframes provide very strict isolation between applications, which can make communication and integration between different microfrontends challenging, resulting in not being able to use `@ng-darwin-wmf` features of sharing and navigating ([Navigation outside the Microfront](./navigation-outside-the-microfront.md)).
- **Performance**: Loading a Microfrontend in an iframe can be slower because each iframe is essentially a separate web page with its own lifecycle and resources.
- **Application State**: Maintaining the application state between different iframes can be complicated and require additional solutions.

### Advantages of using Webpack Module Federation

!!! note
    This is the recommended approach.

- **Dependency Sharing**: Allows sharing dependencies between different Microfrontends, which can improve performance ([Sharing libraries](./sharing-libraries.md)).
- **Lower Overhead**: Since you don't have to load a complete page for each MicroFrontend, the overhead is generally lower.
- **Flexibility**: Offers more flexibility in terms of deployment and maintenance.

In summary, although iframes can be useful in certain scenarios, Webpack Module Federation offers greater flexibility and control, making it generally a better option for implementing microfrontends in a modern ecosystem.
