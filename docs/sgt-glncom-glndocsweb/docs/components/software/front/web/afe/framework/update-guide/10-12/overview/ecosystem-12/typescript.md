# Typescript 4.2

## Stricter checks for internal operator ***in***

In **JavaScript** it is considered a runtime error to use a type that is not an object on the right side of the ***in*** operator. TypeScript 4.2 ensures this can be detected at development time.

```typescript
"foo" in 42
```

It will display the error:

```bash
error! The right-hand side of an 'in' expression must not be a primitive.
```

## Flag `--noPropertyAccessFromIndexSignature`

This ***flag*** guarantees consistency between accessing a field through the syntax using “dot” (`obj.key`) or via ***index*** (`obj["key"]` ) and the way the property is declared in the type.

Without this flag, ***TypeScript*** will allow you to use dot syntax to access fields that are not defined:

```typescript
interface GameSettings {
   // Known initial properties
   speed: "fast" | "medium" | "slow";
   quality: "high" | "low";

   // Assume anything unknown to the interface
   // is a string.
   [key: string]: string;
}

const settings = getSettings();
settings.speed;
//(properties) GameSettings.speed: "fast" | "medium" | "slow"
settings.quality;
//(properties) GameSettings.quality: "high" | "low"

// Access unknown keys are allowed on this object, and are `string`
settings.username;
```

Enabling the `--noPropertyAccessFromIndexSignature` flag will generate an error because the unknown field uses dot syntax instead of indexed syntax.

```typescript
const settings = getSettings();
settings.speed;
settings.quality;

// The right one should be settings["username"];

settings.username;
// Error: Property 'username' comes from an index signature, so it must be accessed with ['username'].
```

## Abstract Construction Signatures

Abstraction is one of the significant features of ***TypeScript***. ***TypeScript*** allows developers to use the ***abstract*** modifier to mark a class as abstract.

To create instances to extract properties and behaviors from abstract classes, developers need to follow a ***concept Basic OOP***, which is to extend the abstract class using a subclass and instantiate objects.

Furthermore, Mixins is one of the cutting-edge methods of ***TypeScript***, which is also related to the same topic.

> **🎓 What are mixins?**
>
> ***Mixins*** is a method of building classes from reusable components using simpler classes.

Before version 4.2, there were some bugs when using ***mixins*** with abstract classes. For example:

```typescript
abstract class Candy {
     abstract getPrice(): number;
}
interface hasPrice {
     getPrice(): number;
}

let newConstructor: new () => hasPrice = Candy;
// Error: Type 'typeof Candy' is not assignable to type 'new () => hasPrice'.
// Cannot assign an abstract constructor type to a non-abstract constructor type.
```

Here contains an error that abstract constructor types cannot be assigned to non-abstract constructor types.
Version 4.2 allows developers to use the abstract modifier in constructor signatures, like this:

```typescript
let newConstructor: abstract new () => hasPrice = Candy;
```

Using ***abstract*** will not prevent you from passing other constructor classes/functions. The main advantage is that it is safe to pass any type of class to a constructor.
Because this helps with ***mixins***, developers can now use ***mixins*** in a way that supports abstract classes.

## Greater visibility of which files are included in your compiled program

The ***TypeScript*** compiler now includes a new flag `--explainFiles`, which generates a list of files that were included in the compilation, as well as the basic logic behind why they exist, in text format simple.

This new feature is a first step toward debugging compile-time issues.

Given a default ***TypeScript*** configuration and a ***index.ts*** file with a simple ***console.log('hello world!')*** , here is an example output with the flag `--explainFiles` .

```bash
node_modules/typescript/lib/lib.d.ts
  Default library
node_modules/typescript/lib/lib.es5.d.ts
  Library referenced via 'es5' from file 'node_modules/typescript/lib/lib.d.ts'
node_modules/typescript/lib/lib.dom.d.ts
  Library referenced via 'dom' from file 'node_modules/typescript/lib/lib.d.ts'
node_modules/typescript/lib/lib.webworker.importscripts.d.ts
  Library referenced via 'webworker.importscripts' from file 'node_modules/typescript/lib/lib.d.ts'
node_modules/typescript/lib/lib.scripthost.d.ts
  Library referenced via 'scripthost' from file 'node_modules/typescript/lib/lib.d.ts'
index.ts
  Root file specified for compilation
```

> The `--explainFiles` flag generates a list of files detailing the files that were generated by TypeScript and the reason for their creation.

## Improved checking of uncalled functions in logical expressions

Due to new improvements in TypeScript 4.2, **TypeScript** uncalled function checks now apply to `&&` and `||` expressions.

Observe the following code:

```typescript
function shouldDisplayElement(element: Element) {
     return true;
}

function getVisibleItems(elements: Element[]) {
     return elements.filter(e => shouldDisplayElement && e.children.length)

}
```

With the ***flag*** `--strictNullChecks` enabled, it will display the following error:

```bash
Error: This condition will always return true since the function is always defined.
Did you mean to call it instead.
```

## Unstructured variables can be explicitly marked as unused

You can now mark unstructured variables as unused by prefixing them with an underscore ***_***.

```typescript
let [_first, second] = getValues();
```

Previously, if the variable ***_first*** was never used later, ***TypeScript*** would throw a ***noUnusedLocals*** error.

Now ***TypeScript*** will recognize that ***_first*** was intentionally named with an underscore because it was not intended to be used.

## Relaxed Rules Between Optional Properties and String Index Signatures

***string*** index signatures are a way of typing dictionary-like objects where you want to allow access with arbitrary keys:

```typescript
const movieWatchCount: { [key: string]: number } = {};

function watchMovie(title: string) {
   movieWatchCount[title] = (movieWatchCount[title] ?? 0) + 1;
}
```

However, for any movie title that is not already in the dictionary, `movieWatchCount[title]` will be ***undefined*** (TypeScript 4.1 added the `--noUncheckedIndexedAccess` option to add ***undefined*** to read an index signature like this).

While it is clear that there must be some **strings** not present in ***movieWatchCount*** , previous versions of ***TypeScript*** treated optional object properties as not assignable to supported index signatures, due to in the presence of ***undefined***.

```typescript

type WesAndersonWatchCount = {
   "Fantastic Mr. Fox"?: number;
   "The Royal Tenenbaums"?: number;
   "Moonrise Kingdom"?: number;
   "The Grand Budapest Hotel"?: number;
};

declare const wesAndersonWatchCount: WesAndersonWatchCount;
const movieWatchCount: { [key: string]: number } = wesAndersonWatchCount;
//error!
// Type 'WesAndersonWatchCount' is not assignable to type '{ [key: string]: number; }'.
// Property '"Fantastic Mr. Fox"' is incompatible with index signature.
// Type 'number | undefined' is not assignable to type 'number'.
// Type 'undefined' is not assignable to type 'number'. (2322)
```

***TypeScript 4.2*** already allows this assignment. However, it does not allow assigning non-optional properties with ***undefined*** in their types, nor does it allow writing ***undefined*** to a specific key:

```typescript
type BatmanWatchCount = {
   "Batman Begins": number | undefined;
   "The Dark Knight": number | undefined;
   "The Dark Knight Rises": number | undefined;
};

declare const batmanWatchCount: BatmanWatchCount;

// Still an error in TypeScript 4.2.
// `undefined` is only ignored when properties are marked optional.
const movieWatchCount: { [key: string]: number } = batmanWatchCount;

// Still an error in TypeScript 4.2.
// Index signatures don't implicitly allow explicit `undefined`.
movieWatchCount["It's the Great Pumpkin, Charlie Brown"] = undefined;
```

The new rule also does not apply to numeric index signatures, since they are assumed to be array-like and compact:

```typescript
declare let sortOfArrayish: { [key: number]: string };
declare let numberKeys: { 42?: string };

// Error! Type '{ 42?: string | undefined; }' is not assignable to type '{ [key: number]: string; }'.
sortOfArrayish = numberKeys;
```
