# Darwin Spring Boot Logging ![4.3.3-RELEASE](https://img.shields.io/badge/4.3.3-RELEASE-FF073D)

![GA](https://img.shields.io/badge/GA-C81D11)

## Description

The `Darwin Spring Boot Logging` library was born out of the need to generate traces in a specific Json format so that these traces can be managed from the monitoring area.

The library is prepared to be able to generate several types of traces in accordance with the [format defined by architecture](https://sanes.atlassian.net/wiki/spaces/SANACLOUD/pages/16515078098/DLP+-+Common+and+Specific+Log+Fields).

The types of traces supported by the library are:

- Activity traces: These are automatically generated traces that allow tracing general information of all the requests, information about the source application, time to complete the request, etc. These traces are generated both in the
    microservices and in the micro-gateway.

- Functional traces: These are traces generated manually or automatically and allow the input and output fields of a request to be traced. These traces can be generated both in the microservices and in the micro-gateway, although the norm is to
    generate them only in the micro-gateway and to enable them in the micros in exceptional cases.

- Technical traces: Traces generated by developers to solve possible errors or traces with certain technical information.

- Security traces: Traces managed by the security team, which define where and how to generate these types of traces.

- It has automatic mechanisms that are responsible for adding the HTTP header 'User-Agent' to any request made through the HTTP clients supported by Darwin.

- For complex scenarios, where Darwin's default configuration does not meet all the needs of a project, the logging module exposes a functional API for the creation and customisation of the logging context.

## Functionalities

The `Darwin Spring Boot Logging` library will detect the type of application it is running in, autoconfiguring only those functionalities that apply to that environment. To define the execution environment of a `Spring Boot` application we will make
use of the values defined in [WebApplicationType](https://docs.spring.io/spring-boot/docs/3.1.12/api/org/springframework/boot/WebApplicationType.html), being able to apply it by means of a property or code:

- To make use of the property:

<!-- -->

    spring.main.web-application-type=NONE #REACTIVE, SERVLET

- To do this through code we will make use of the `SpringApplicationBuilder` class:

<!-- -->

    @SpringBootApplication
    public class Application {
        public static void main(String[] args) {
            new SpringApplicationBuilder(Application.class)
                    .web(WebApplicationType.NONE) // .REACTIVE, .SERVLET
                    .run(args);
        }
    }

If no application type is defined, `Spring Boot` will automatically select the environment by auto-discovery of project dependencies:

- If it finds `starter spring-web` it will boot in `SERVLET` mode.

- If it finds the `starter spring-webflux` it will start in `REACTIVE` mode.

- If it finds both `starters` it will boot in `SERVLET` mode.

- If neither of the above `starters` is found, it will boot in `NONE` mode.

The application types that the library is able to detect are:

- ***NotWeb***: The application does not run as a web application and therefore should not start an `embedded web server`, but detects the presence of the `restTemplate` and/or `webClient` dependency, so it auto-configures itself with the `Darwin`
    interceptors.

- ***Servlet***: The application runs as a `Servlet` based web application and therefore should start an `embedded web server`, by default `Tomcat`.

- ***Reactive***: The application runs as a reactive web application based on `WebFlux` and therefore should start an `embedded web server`, by default `Netty`.

The auto-configurations per application type shall be hierarchical, i.e:

- ***NotWeb***: NotWeb (base configuration that is always applied)

- ***Servlet***: Servlet &gt; NotWeb[^1].

- ***Reactive***: Reactive &gt; NotWeb[^2].

The `Darwin Spring Boot Logging` library provides the following functionalities depending on the application type:

### Traces format

Darwin Logging supports three traces format/patterns: **SPAIN format** (compatibility with old Darwin versions), **GLOBAL format** and **GLUONLOG format**. This can be configured using `darwin.logging.format` property (by default GLOBAL format is
configured).

### Manual Fatal level traces

- The `ExtendedLogger` class is configured giving projects the possibility to generate a `FATAL` level trace.

### Manual functional traces

- If the application is non-reactive (no `Reactor` dependency found), the `FunctionalLogHelper` class is configured giving projects the possibility to generate a functional trace manually.

- If the application is reactive (the Reactor dependency is found), the `FunctionalReactiveLogHelper` class is configured (with the same functionality as its equivalent FunctionalLogHelper) but prepared for reactive environment.

- For both kind of applications, the functional information can be **sensitised in order to hide the sensible data**.
  The Functional helpers offer a methods that it accepts as input parameter a list of fields to hide.
  Additionally, it is possible to add **custom information using the customFunctionalLog Map**.

### Manual security traces

- If the application is non-reactive (the `Reactor` dependency is not found), the `SecurityLogHelper` class is configured giving projects the possibility to generate security traces manually.

- If the application is reactive (the Reactor dependency is found), the `SecurityReactiveLogHelper` class is configured (with the same functionality as its equivalent SecurityLogHelper) but prepared for reactive environment

### Manual activity traces

This functionality is ***EXCLUSIVE*** for ***NotWeb*** environments (not available in ***Servlet*** or ***Reactive***):

- If the application is non-reactive (no `Reactor` dependency found), a `Bean` of type `LoggingService<Void>` is exposed, allowing to generate an activity trace manually.

- If the application is reactive (the `Reactor` dependency is found), two bean are exposed: a `Bean` of type `LoggingService<Mono<Void>>` and another `Bean` of type `LoggingService<Consumer<Signal<?>>`, allowing to generate an activity trace
    manually through both of them.

### Micrometer tracing integration

This library enables tracing using Micrometer Tracing with the Brave implementation by including the `io.micrometer.micrometer-tracing-bridge-brave` dependency.

#### Instrumentation of ThreadPoolTaskExecutor

Additionally, we add to the instrumentation of the `ThreadPoolTaskExecutor` a new `TaskDecorator` bean provided by the library.

This `TaskDecorator`, in addition to propagate the contexts registered in `ContextRegistry` (already achieved from Core module), is used to create a **new Observation for the thread execution**, propagating the tracing Context.

#### Instrumentation for reactive streams

The preferred way of propagating elements through a Reactor stream is **not via ThreadLocals but through Reactor Context**. Darwin Logging requires some information from context (like tracing) to be in ThreadLocals to complete logs information. We
can achieve this propagation with Reactor-Micrometer's integration using a manual or an automatic instrumentation as we showed in [How to propagate context from/to Reactor
stream](../darwin-spring-boot-core/README.md#how-to-propagate-context-fromto-reactor-stream).

##### Manual instrumentation (Default)

By default, the **Reactor-Micrometer context propagation is in "LIMITED" mode**. This mean that ThreadLocals aren't loaded from/to Reactor ContextView automatically, it's up to the user to do it.

If you want to log any information during a reactive stream **Reactor** gives you two operators, `tap()` and `handle()` which, if Micrometer Context Propagation library is on the classpath, they will set ThreadLocal values from ContextView for the
code execution they contain.

The difference between these two operators whether if they are going to modify the stream content or not. If we are just going to "listen" the stream and take some actions we'll use `tap()` operator, but if we're going to modify the content of the
stream we'll use `handle()` operator.

For example, in order to trace manually using `tap()` operator:

    import org.springframework.web.bind.annotation.RestController;
    import reactor.core.observability.DefaultSignalListener;

    @RestController
    public class SomeController {

        @GetMapping("/hello")
        public Mono<String> hello() {
            return Mono.just("Hello!")
                .tap(() -> new DefaultSignalListener<>() {
                    @Override
                    public void doOnNext(String value) throws Throwable {
                        log.info("Log with next value: {}", value);
                    }

                    @Override
                    public void doOnComplete() throws Throwable {
                        log.info("Log when stream completed");
                    }

                    @Override
                    public void doOnError(Throwable error) throws Throwable {
                        log.error("Log when error received", error);
                    }
            });
        }
    }

And to trace manually while modifying the content of the stream using `handle()`:

    import org.springframework.web.bind.annotation.RestController;

    @RestController
    public class SomeController {

        @GetMapping("/hello")
        public Mono<String> hello() {

            return Mono.just("Hello")
                    .handle((content, sink) -> {
                        String complete = content + "world!";
                        log.info("Answer is {}", complete);
                        sink.next(complete);
                });
        }
    }

Finally, if you are **using a reactive stream from within a servlet application** you also need first to get ThreadLocal information and set Reactor Context. This can also be done using a Reactor operator, that together with the Micrometer
context-propagation library propagate ThreadLocals to Reactor Context. You can use `contextCapture` like this:

    import org.springframework.web.bind.annotation.RestController;

    import reactor.core.observability.DefaultSignalListener;

    @RestController
    public class SomeController {

        @GetMapping("/hello")
        public String hello() {
            // Modify DarwinContext
            DarwinContextHolder.setCurrentContext(newDarwinContext);

            return Mono.just("Hello!")
                .tap(() -> new DefaultSignalListener<>() {
                    @Override
                    public void doOnNext(String value) throws Throwable {
                        log.info("New DarwinContext loaded");
                    }
                })
                .contextCapture()
                .block();
        }
    }

!!! note

    For more information about how to use instrumentation to observation: [Instrumentation of reactive libraries](https://micrometer.io/docs/observation#instrumentation_of_reactive_libraries)

##### Automatic instrumentation

To enable automatic instrumentation and trace complete logs from any Reactor operator you can use `darwin.core.reactor.context-propagation` with "AUTO" value as we explained [here](../darwin-spring-boot-core/README.md#reactor-context-propagation).

Now you can trace complete logs like this:

    import org.springframework.web.bind.annotation.RestController;
    import reactor.core.observability.DefaultSignalListener;

    @RestController
    public class SomeController {

        @GetMapping("/hello")
        public Mono<String> hello() {
            return Mono.just("Hello")
                .map((String str) -> {
                    log.info("Adding world to string response");
                    return str + "world";
            });
        }
    }

!!! tip "Caution"

    **Enabling this feature can lead to poor performance** because of wrapping the execution of each operator in order to propagate all managed contexts.

### Interceptor RestTemplate

- A `ClientHttpRequestInterceptor` named `LoggingInterceptor` is injected to propagate the HTTP header **User-Agent** from the incoming request. This header is used by the logging library to identify the originating application making the request.
    In case the W3C headers (***tracestate*** and ***traceparent***) are reported in the request and W3C TraceContext support is disabled, the interceptor shall propagate them without altering their content.

!!! tip "Caution"

    It is necessary for the project to register a `RestTemplate` type bean and stereotype it with the `@DarwinQualifier` annotation for the instrumentation to be applied. If the project registers a `RestTemplate` bean without the
    `@DarwinQualifier` annotation, it is understood that you want to use the `RestTemplate` provided by `Spring` by default instead of the one configured by `Darwin` so the instrumentation will **NOT** be applied.

### WebClient Interceptor

- Beans `WebClient` and `WebClient.Builder` are configured with an `ExchangeFilterFunction` with type `LoggingFilter` with the same functionality as the `LoggingInterceptor` but valid for both `Reactive` (`Reactor` dependency is included) and non
    `Reactive` environments.

!!! tip "Caution"

    It is necessary for the project to register a `WebClient.Builder` or `WebClient` bean for the instrumentation to be applied. If the project creates an instance of `WebClient` with the keyword `new`, the instrumentation will
    **NOT** work.

### Sampling

In distributed systems, the volumes of traces generated by each interaction can be very large and this can lead to overloads that compromise the system or affect its performance. One mechanism to reduce the amount of information collected by the
system is sampling. Darwin allows HTTP requests and messaging events to be sampled so that only a certain number of traces are dumped into the monitoring system. The selection and volume of traces to be reported depends on the sampling policy
chosen.

Sampling is set at the first operation of a run. Once the decision to report or not the traces is made, it is propagated to each of the remaining operations of that interaction, i.e. the decision is applied to the whole *downstream* of the request.
For the calculation of the sampling decision, `Brave` library makes use of a [Sampler](https://javadoc.io/doc/io.zipkin.brave/brave/5.15.1/brave/sampler/Sampler.html).

Darwin's sampling policy sets, by default, that all traces are sent to the monitoring system. This strategy can be overridden by defining a `Sampler`.

In Darwin, activity traces are sampled according to the defined sampling policy.

For functional traces, by default, no sampling policy is applied, and they are always sent to the monitoring system. To enable sampling on functional traces, use the `darwin.logging.functional.mode` property. For more information, see
[configuration](#configuration).

For technical traces, by default, no sampling policy is applied, and they are always sent to the monitoring system. In order to enable sampling on technical traces, it is necessary to enable the use of the `Threshold` using the
`darwin.logging.threshold.mode` property with the `SAMPLED` value. For more information, see [Threshold](#threshold) section.

#### Samplers

Zipkin Brave offers a number of ready-to-use default `Samplers`:

- [RateLimitingSampler](https://javadoc.io/doc/io.zipkin.brave/brave/5.15.1/brave/sampler/RateLimitingSampler.html)

The Rate Limiting `Sampler` is based on Brave's `Sampler` [RateLimitingSampler](https://javadoc.io/doc/io.zipkin.brave/brave/5.15.1/brave/sampler/RateLimitingSampler.html) and allows you to choose the number of traces per one second interval. The
minimum number is 0 and the maximum is 2,147,483,647 (max int). Through the use of the `management.tracing.sampling.rate` property, a custom rate of traces per second can be set.

- [ProbabilityBasedSampler](https://javadoc.io/doc/io.zipkin.brave/brave/5.15.1/brave/sampler/ProbabilityBasedSampler.java)

This `Sampler` bases the decision to apply sampling on a probability. This can be set through the `management.tracing.sampling.probability` property. For example, the value *1.0f* would mean that 100% of requests would be sampled. The precision only
supports integers, minimum probability is 0.01, or 1% of traces. There is no support for 0.1% of the traces.

!!! info "Important"

    Once the `management.tracing.sampling.rate` or the `management.tracing.sampling.probability` property is set, its associated `Sampler` will be the one used for sampling decision-making in the application.

In case none of the provided `Samplers` meet the sampling needs required by the project, a custom `Sampler` can be created. The implementation will be as simple as creating a class that extends the abstract `Sampler` class and implementing the
decision-making algorithm:

    import brave.sampler.Sampler;

    public class CustomSampler extends Sampler {

        private final static int MAX_REQUEST = 10;

        private int counter;

        private final int rate;

        public CustomSampler(Integer rate) {
            this.counter = 0;
            this.rate = rate;
        }

        @Override
        public boolean isSampled(long ignoredTraceId) {
            if (counter == MAX_REQUEST) {
                counter = 0;
            }
            if (counter < this.rate) {
                counter++;
                return true;
            } else if (counter < MAX_REQUEST) {
                counter++;
                return false;
            }
            return false;
        }
    }

In this example a sampling policy is set up where the number of traces to be reported for every 10 HTTP requests or events received is allowed to be chosen.

In case the default sampling strategy does not cover the needs required by the project and the chosen sampling policy cannot be configured by using properties, a `@Bean` of type `Sampler` must be created. For example, the following autoconfiguration
could be used:

    import brave.sampler.Sampler;
    import com.santander.darwin.logging.config.LoggingAutoConfig;
    import org.springframework.boot.autoconfigure.AutoConfigureBefore;
    import org.springframework.context.annotation.Bean;
    import org.springframework.context.annotation.Configuration;

    @Configuration(proxyBeanMethods = false)
    @AutoConfigureBefore(LoggingAutoConfig.class)
    public class AppAutoConfiguration {

        @Bean
        public CustomSampler sampler() {
            return new CustomSampler(5);
        }
    }

Finally, in case it is necessary to establish a sampling strategy where traces are **never** sent to the monitoring system, the following configuration can be added which creates a `Sampler` that complies with such a policy:

    import brave.sampler.Sampler;
    import com.santander.darwin.logging.config.LoggingAutoConfig;
    import org.springframework.boot.autoconfigure.AutoConfigureBefore;
    import org.springframework.context.annotation.Bean;
    import org.springframework.context.annotation.Configuration;

    @Configuration(proxyBeanMethods = false)
    @AutoConfigureBefore(LoggingAutoConfig.class)
    public class AppAutoConfiguration {

        @Bean
        public Sampler sampler() {
            return Sampler.NEVER_SAMPLE;
        }
    }

!!! info "Important"

    The [Sampler](https://javadoc.io/doc/io.zipkin.brave/brave/5.15.1/brave/sampler/Sampler.html) class offers another default implementation:
    [AlwaysSampler](https://javadoc.io/doc/io.zipkin.brave/brave/5.15.1/brave/sampler/Sampler.html#ALWAYS_SAMPLE). This strategy always samples the request, i.e. they are always sent to the monitoring system. This is the default `Sampler` used by
    Darwin.

#### Threshold

The threshold is a special type of sampling provided by Darwin that can be enabled by using the `darwin.logging.threshold.level` property. It allows a log level to be set as a condition so that only those technical traces and activity that meet it
are sent to the monitoring system. For example, if a threshold log level is set to `WARN`, only technical traces with that level will be sent to Kibana. In case the log level for the threshold is set to `ERROR`, apart from limiting the sending of
technical traces to that level, activity traces that are marked as error traces will also be sent to the monitoring system.

By default, all traces shall be sent to the monitoring system. To enable sampling for traces managed through the threshold, the sampling mode must be changed through the `darwin.logging.threshold.mode` property.

It is important to add that this type of sampling is only applied on the Kafka appenders that are in charge of routing the requests to Kibana. This means that we could define a threshold as `ERROR` and a loglevel for a packet with value INFO, which
means that all messages with loglevel `INFO` or lower will be shown on the console, but only messages generated with loglevel `ERROR` will be routed to Kibana.

By default, the threshold is disabled. To enable this feature, just set a log level:

    darwin:
     logging:
        threshold:
          level: WARN

Once the use of the threshold is enabled, note that the sampling mode is set to `ALWAYS` by default, i.e. the traces are always sent to Kibana. To apply the sampling policy, the `SAMPLED` mode must be set through the `darwin.logging.threshold.mode`
property:

    darwin:
     logging:
        threshold:
          level: WARN
          mode: SAMPLED

!!! info "Important"

    The threshold can be used together with the capabilities offered by the rest of the `Samplers`, being able to limit the sending of activity traces by means of the sampling policy and the `ERROR` log level, since the activity
    traces only contemplate the `INFO` and `ERROR` levels. This means that when defining a Sampler + a threshold, both conditions must be met in order to send the activity trace to Kibana.

### Automatic traces

#### Activity traces

These are automatically generated traces that allow tracing general information of all the requests, information about the source application, time to complete the request, etc. These traces are generated both in the microservices and in the
micro-gateway.

##### Partenon Activity traces

If Darwin Logging library is included together with `Darwin Spring Boot Partenon module` or just the original `Partenon Spring Boot library`, all TrxOp executions are going to write an ActivityLog with the following customization:

- log: "End of TrxOp execution".

- url: @PartenonBean entity information.

- method: "TrxExecution".

- returnCode: 202 (Ok or unknown), 400 (Architectural error) or 500 (application error).

- customLog.trxTransaction: TrxOp Transaction.

- customLog.trxOperation: TrxOp Operation.

- customLog.trxVersion: TrxOp Version.

- customLog.trxCodResolution: TrxOp resolution code (if exist).

#### Functional traces

These traces are generated both in the microservices and in the micro-gateway (although it is normal to generate them only in the micro-gateway and enable them in the micros in exceptional cases) and allow the input and output fields of a request
to be traced.

!!! note

    For any request with a certain type of content (APPLICATION\_PDF, IMAGE\_GIF, IMAGE\_JPEG, IMAGE\_PNG, MULTIPART\_FORM\_DATA, TEXT\_MARKDOWN) the content of the request body will not be added to the trace.

!!! note

    Any request body that exceeds 1 MB in size is not added as a trace in the functional log

##### Obfuscation

The functional data (input and output) can be hidden by using the `ObfuscateFunctionalLog` annotation. This accepts a set of sensitive fields as input parameter in order to define that values have to be hidden. This process only is applied to
endpoints that they are defined in the list of functional endpoints and their controller methods or rest controller classes are marked with the annotation `ObfuscateFunctionalLog`. Finally, The `ObfuscateFunctionalLog` annotation can be used in both
`Reactive` web applications and `Servlet` web applications.

!!! note

    For more information about how to use the `ObfuscateFunctionalLog` annotation, consult the [How to obfuscate Functional data](#obfuscate-functional-data) section

### Gravity appender

Darwin Logging offers a Gravity configuration
to add the necessary components for tracing relevant information about the execution of BPS transactions.
This feature creates a logger for each class and/or package specified by the configuration (by
default, only for `BpsVerify` class)
and adds a Gravity Kafka appender to each one of them for sending the traces to the `Gravity System Monitoring`.
Additionally, the Gravity configuration allows developers to define a topic, appender level, and logging pattern to each
package/class defined.

### GLUON features

By default, Darwin Logging is compliant with GLUON observability requirements. These requirements can be enabled or disabled by the property 'darwin.logging.observability.gluon-features.enabled'. This property manages and overrides the default
behaviour of the following properties and functionalities:

| Name                                            | Default value (GLUON enabled) | Default value (GLUON disabled) | Description                                                                           |
|-------------------------------------------------|-------------------------------|--------------------------------|---------------------------------------------------------------------------------------|
| darwin.logging.observability.filter.enabled     | 'true'                        | 'false'                        | Flag to enable/disable the property `darwin.logging.observability.filter.white-list`. |
| management.tracing.propagation.type             | 'B3'                          | 'W3C'                          | Sets the propagation type.                                                            |
| management.tracing.brave.span-joining-supported | 'true'                        | 'false'                        | Enables regardless of whether client and server spans share the same ID.              |
| management.tracing.baggage.enabled              | 'true'                        | 'true'                         | Enables Micrometer Tracing baggage propagation                                        |

Therefore, enabling `darwin.logging.observability.gluon-features.enabled` changes the default behaviour:

- Uses B3 multiple header propagation

- Adds joined span support

- Activates Observability filter

- Sets traceId to 64 bits

## Installation and configuration

To add the library to any project, the maven dependency must be included in the `pom.xml` file:

    <dependency>
            <groupId>com.santander.darwin</groupId>
            <artifactId>darwin-spring-boot-starter-logging-kafka</artifactId>
    </dependency>

If we include this library in a `Spring Boot` application without further dependencies, the default configuration will be the one corresponding to ***NotWeb***, therefore the mechanism that will allow us to enable any of the
[Functionalities](#functionalities) that the library is able to manage will be through the inclusion of dependencies. For this purpose, the following table describes the dependencies to be included by application type.

| Application Type            | Environment | Dependencies                                                                                                                                                     |
|-----------------------------|-------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| WebApplicationType.NONE     | NotWeb      | <ul><li>com.santander.darwin:<strong>darwin-spring-boot-logging</strong></li></ul>                                                                               |
| WebApplicationType.SERVLET  | Servlet     | <ul><li>com.santander.darwin:<strong>darwin-spring-boot-logging</strong></li><li>org.springframework.boot:<strong>spring-boot-starter-web</strong></li></ul>     |
| WebApplicationType.REACTIVE | Reactive    | <ul><li>com.santander.darwin:<strong>darwin-spring-boot-logging</strong></li><li>org.springframework.boot:<strong>spring-boot-starter-webflux</strong></li></ul> |

!!! info "Important"

    Although you can add the dependencies manually and the application type, the archetype has been redesigned to include all configuration possibilities, so we strongly recommend using
    Darwin Archetypes to avoid errors.

Also, there is the possibility of adding a library basic version.
This starter creates the Darwin Logging configuration without the Kafka Appenders, only Console Appenders.
The maven dependency must be included in the `pom.xml` file:

    <dependency>
            <groupId>com.santander.darwin</groupId>
            <artifactId>darwin-spring-boot-starter-logging-basic</artifactId>
    </dependency>

By default, the configuration for this `starter` configures as the Console pattern a non-human readable format
(**JSON**).
This format is the same one that Darwin Logging uses for the Kafka Appenders when the application loads this capacity.

!!! info "Important"

    Remember that the configuration associated with this `starter` only configures **Console appenders**.
    **Ensure** that the execution environment has the necessary capacities
    to read the logs from the console and to send them to the respective monitoring system.

### Basic configuration

By default, the minimum required configuration for the Darwin Logging library is composed by the **app-key** and **paas-app-version**, together with the **serviceName** property (is not necessary to define, by default it is formed with the env
variables ${PROJECT\_NAME}\_${DARWIN\_REGION}) they will identify the application in the monitoring systems:

    darwin:
     app-key: demoapp
     logging:
        paas-app-version: "@project.version@"

!!! warning

    For gluon app, it is required the property *darwin.app-name* instead of *darwin.app-key*. In the case that both are reported, the value that will be taken will be that of the appName.

Also, **entity** and **platform** properties are set by default with "ESP" and "Darwin" values.

With this configuration, all traces will be displayed only by console with an INFO level.

#### Gluon configuration

If "GLUONLOG"
value is configured in *darwin.logging.format* property, there are some more properties
to define to identify the application in the monitoring systems:
app-key, company, componentName, componentId, componentType, and appId.

    darwin:
     app-name: demoapp
     logging:
       format: "GLUONLOG"
       gluon-log:
         appId: "gluon-test-micro-reactive"
         company: "gluon-test"
         componentName: "gluon-test-reactive"
         componentId: "gluon-micro-reactive"
         componentType: "gluon-test-micro"

With this configuration, all traces will be displayed only by console with an INFO level.

#### Old format basic configuration

!!! info "Important"

    Old format (**SPAIN format**) will be deprecated in the following version.

If "SPAIN"
value is configured in *darwin.logging.format* property there are some more properties
to define to identify the application in the monitoring systems:
app-name, system, subsystem, application, subapplication and paas-app-version.
It will
not be necessary to define the **paasproject**,
since by default it is formed with the variables ${PROJECT\_NAME}\_${DARWIN\_REGION}.

    darwin:
     app-key: demoapp
     logging:
        format: SPAIN
        system: DEMO
        subsystem: DEMO
        application: DEMO
        subapplication: DEMO
        paas-app-version: "@project.version@"

With this configuration, all traces will be displayed only by console with an INFO level.

!!! info "Important"

    Both `APP_NAME` and `HOSTNAME` are values read from the environment variables. It is mandatory to set them in the environment in order to be shown in both kibana traces and console traces. `DARWIN_REGION` can be defined as
    environment variable or as a property in the ***application.yaml***. It is recommended to set it as environment variable in order to have a dynamic value in function of the region of the PaaS where the application is deployed. For more information
    about patterns, checks [Pattern configuration](#pattern-configuration) section.

#### Add generic trace level to technical logs

If we wanted to specify a generic trace level we would have to indicate the root trace level.

##### Properties

    logging.level: #(1)
     root: DEBUG #(2)
    darwin:
     app-key: demoapp
     logging:
        paas-app-version: "@project.version@"

1. We define the logging.level property that Spring uses to define the different trace levels we may need.

2. We give a value to the root logger, this value will be the value of all the technical logs that we do not define implicitly. Possible values are DEBUG, INFO, WARN, ERROR and FATAL.

#### Add sending logs to Kafka

With the configuration defined so far, the library will automatically generate activity traces and the appropriate technical traces, but they will not be sent to Kafka for further processing. To achieve this we will have to additionally configure
the Kafka server(s) to send them to:

    logging.level:
     root: INFO
    darwin:
     app-key: demoapp
     logging:
        paas-app-version: "@project.version@"
        kafka:
          server: kafkadarwin.santander.dev.corp:9092 #(1)

1. Path to the Kafka server to which the traces will be sent, in the format host:port (e.g. localhost:1243).

**It will not be necessary to define the topics** as they should always be sent to the default topics.

If you do not have or do not have access to the Kafka server, they can be ignored and the trace system will be loaded without the Kafka appender.

#### Sending logs to Gravity Logging System

Logging library allows projects
to add an extra configuration for logging relevant information about execution of BPS transactions.
This configuration is disabled by default, and it must be enabled through the property `darwin.logging.gravity.enabled.`

According to the configuration,
a logger is created for each class and/or package
specified by the `darwin.logging.gravity.appender.package-info` property
(by default, only for the BpsVerify class with level INFO and without a topic defined)
and a Gravity Kafka appender is added to each one of them for sending the traces to the Gravity Logging System.

**The Gravity configuration enables the use of custom topics for each package/class specified in the properties.**
It is possible to define a package/class without a specific topic or logging pattern;
the configuration will use the topic defined in the `darwin.logging.gravity.kafka.topic` (topic by default).
If no topics are specified, the Gravity Kafka Appenders will not be loaded.
If no pattern is defined, the appenders will log using the default Gravity logging pattern.

Additionally,
Darwin Gravity configuration allows developers
to define a custom log-level, through the `darwin.logging.gravity.appender.package-info[@].level` property,
for the Gravity Kafka appender associated with each package/class.

!!! info "Important"

    It is crucial to keep in mind that, by each package/class defined,
    the configuration creates a `logger` with the log-level defined
    (`darwin.logging.gravity.appender.package-info[@].level`) for the Gravity Kafka Appender.
    The log-level used by the `logger` establishes the level in which the traces will be emitted (equal or higher level).
    The Gravity Kafka appender only sends traces with the same or higher level than the `logger` log-level.
    If it is necessary to set a custom log-level for the `logger` associated with package/class,
    the `logging.level` property must be used.
    This property value **takes precedence** over level
    defined in the `darwin.logging.gravity.appender.package-info[@].level` property,
    and it will be taken to create the `logger`.

    To clarify the behaviour of the Darwin Gravity configuration, let's see an example:

        logging.level:
         com.isb.rigel.srvcimpl.trxop.TrxOpServiceImpl.BpsVerify: DEBUG (1)
        darwin:     
         logging:
            gravity:
              appender:
                package-info:
                  - name: com.isb.rigel.srvcimpl.trxop.TrxOpServiceImpl.BpsVerify (2)
                    level: ERROR

    This configuration will create a `logger` for the `com.isb.rigel.srvcimpl.trxop.TrxOpServiceImpl.BpsVerify` class with the log-level
    defined in the `logging.level` property
    (DEBUG).
    Additionally,
    it will create a Gravity Kafka appender for the `com.isb.rigel.srvcimpl.trxop.TrxOpServiceImpl.BpsVerify` class
    with the log-level defined in the `darwin.logging.gravity.appender.package-info[@].level` property (ERROR).

    The `logger` will emit traces from the DEBUG level to FATAL level,
    but the Gravity Kafka appender will only process traces from the ERROR level to FATAL level,
    never send traces from the DEBUG or INFO level to the `Gravity Logging System`.

!!! note

    Precedence of the logging levels: `ALL < TRACE < DEBUG < INFO < WARN < ERROR < FATAL < OFF`.

!!! warning

    The `darwin.logging.gravity.appender.packages` property has been marked as deprecated, and it will be deleted in the next version.
    For this version, the values defined through this property will still be read and its values
    applied to configuration.

To use this feature using the packages value by default, we will have to additionally configure the `Gravity` properties for configuring the Gravity Kafka server(s), to set the topic where to send the traces, and to define the technical-packages
that they have to generate traces in order to send them to the Gravity broker:

    darwin:
     logging:
        gravity:
            enabled: true
            kafka:
              topic: ESP_SAN_CERT_GAA_FUNC_MICROS_TRX_MET (1)
              server:
               - 180.88.19.49:9096 (2)
               - 180.88.19.48:9096
               - 180.88.19.47:9096
               - 180.88.19.46:9096
               - 180.88.19.45:9096
              properties:
                request.timeout.ms: 5000

1. Topic where to send the messages from 'com.isb.rigel.srvcimpl.trxop.TrxOpServiceImpl.BpsVerify' class.

2. The List of hosts to the Gravity Kafka server to which the traces will be sent, must be in the format host:port (e.g. localhost:1243).

By default, only the class `com.isb.rigel.srvcimpl.trxop.TrxOpServiceImpl.BpsVerify` will generate `Gravity` traces.

!!! info "Important"

    It will be necessary to define the topics.

!!! warning

    During the configuration, the connection with the broker is checked. If the application cannot connect to the Gravity Kafka server, the Gravity Kafka Appender won't be loaded in the configuration and the traces won't appear
    in the Monitoring system.

The log level of the **technical-packages loggers** can be customised using the `logging.level` property.
In addition,
the log level for the Darwin Technical Kafka Appender added to each technical-package logger also can be customised
using the
following property: `darwin.logging.gravity.appender.technical-level`.

!!! info "Important"

    To disable the use of the Darwin Technical Kafka Appender in the packages/classes that generate `Gravity` traces,
    the `darwin.logging.gravity.appender.technical-level` property must be set to `OFF`.
    ***The 'OFF' level value has to be defined with quotes ('')***. In other hand, the application fails during start-up. 

Finally, for adding new packages and/or classes to the configuration, the `darwin.logging.gravity.appender.package-info` property must be used as follows:

    darwin:
     logging:
        gravity:
          enabled: true
          appender:
            package-info:
              - name: darwin.some.package.processor (1)
                level: DEBUG
              - name: darwin.some.package.transaction (2)
                level: ERROR
                topic: transaction-topic
              - name: partenon.another.package.execution (3)
                level: WARN
                topic: execution-topic
                pattern: '{"logLevel":"%level",
                         "Logs": %m,
                         "timeStamp":"%d{${timeStampPattern}}{UTC}Z",
                         "project": "${appKey}",
                         "customField":"transaction-topic"
                         } %ex{0}%n'
        kafka:
          topic: ESP_SAN_CERT_GAA_FUNC_MICROS_TRX_MET (4)
          server:
           - 180.88.19.49:9096
          properties:
            request.timeout.ms: 5000

1. Package/class defined **without** a specific topic. The configuration will use the default topic.

2. Package/class defined with a specific topic. The configuration will create a custom Kafka appender to send to traces to its own topic.

3. Package/class defined with a specific topic and custom pattern. The configuration will create a custom Kafka appender to send to traces to its own topic.

4. Topic by default. This topic is used when a package/class defined doesn't have its own topic.

!!! note

    If it is necessary a custom configuration, there are [more properties](#gravity-properties) in order to set a specific parametrization.

#### Sending Logs to Console without Kafka

If no Kafka server is configured, the server configuration is invalid, or there is no kafka configuration, **all traces** will be sent to the console in their respective console pattern.

An example of no kafka server configuration:

    logging.level:
     root: INFO
    darwin:
     app-key: demoapp
     logging:
        paas-app-version: "@project.version@"
        kafka:
          server:

### Pattern configuration

The logging library sets a default value for each of the trace generation patterns
used in the `appenders` created in the configuration phase.
These patterns can be modified through the properties file.
To do so, simply list the properties to be
configured (in key-value format) under the `darwin.logging.pattern` property.
The available patterns are the following: `security`, `frontend`, `console`,
`technical`, `functional`, `activity`, `metrics`, `console-metrics`.

    darwin:
      logging:
        pattern:
          security: '{%X{securityLogData}'
          frontend: '{"\"navigator\" : %X{fe-navigator}'
          console: '%X{X-B3-SpanId}'
          technical: '{\"threadId\": "%threadName"}'
          functional: '%X{X-B3-SpanId}'
          activity: '%X{inputTimeStamp}'
          metrics: '%m'
          console-metrics: '%d{yyyy-MM-dd HH:mm:ss.SSS} - %m'

In this example, the default value of each of the trace generation patterns in the library properties has been modified.

There are three out-of-the-box patterns within the Darwin Logging library for Activity, Technical, Functional and Security traces, you can configure which one will you use with the property `darwin.logging.format`:

    darwin:
      logging:
          format: GLOBAL # Or SPAIN, GLUONLOG

!!! warning

    Next fields are **deprecated** in GLUONLOG format and they are going to remove in future: *region, appkey, serviceName, platform, entity, paasAppVersion*. For these fields, if there is no value, the key will not be sent
    (except appKey, which will always be sent).

By default, **GLOBAL** format will be used. All possible values for each of the patterns are shown below.

#### Security pattern

### Kafka client configuration

Logging library uses different kind of Kafka components in order to connect to Kafka broker of the monitoring system. First, the connection with the Kafka broker is checked by a validator. This validator uses a Kafka AdminClient in order to validate
the communications. Once the connection has been tested, Kafka Appenders are added to the Logging configuration in order to send traces to the system monitoring. Each Kafka Appender is formed by a Kafka producer.

The logging library allows you to configure any additional properties of the Kafka client and the Admin client used by Kafka connection validator. To do so, we simply list the properties to be configured (in key-value format) under the
`darwin.logging.kafka.properties` property.

In this way, we can configure the **timeout on the connection to the Kafka server**, by default 30 seconds for Kafka clients and 5000 milliseconds for Kafka connection validator, by defining the value of the `request.timeout.ms` property as shown in
the following example:

    darwin:
      app-key: darwin
      logging:
        kafka:
          server: ${env.logging-server}
          properties:
            request.timeout.ms: 5000

In the same way, you can define any client property, which can be found in the [official Kafka documentation](https://kafka.apache.org/35/documentation.html#configuration).

### Configure unique Kafka topic

By default, each type of log is sent from Darwin Kafka appenders to a different Kafka topic defined that can be customized (you can see the properties and default values [kafka](#kafka)).

But you can configure the Logging library to **send all logs to the same topic** using `darwin.logging.kafka.unique-topic` property:

    darwin:
      app-key: darwin
      logging:
        kafka:
          server: ${env.logging-server}
          unique-topic: darwin-logs-topic

### How to configure the Retry for connection validation with Kafka

The configurable Retry instance in the logging library is:

- **KafkaLoggingConnection:** Controls the number of retries and timeout for connection validation with Kafka.

#### Retry

The default settings for Retry (number of retries and the time delay between retries) are:

- **maxAttempts:** The maximum number of retries. The default will be 3 retries.

- **waitDuration:** A fixed waiting time between retries. Default ***500*** \[ms\].

If you want to change the default configuration for Retry, you must modify the following parameters:

    resilience4j.retry:
      instances:
        KafkaLoggingConnection:
          maxAttempts: 3
          waitDuration: 500

!!! note

    For more information about the operation or additional parameters of Retry, please refer to the product documentation: [Resilience4j Retry](https://resilience4j.readme.io/docs/retry).

### W3C TraceContext Support

Darwin supports [W3C Trace Context](https://w3c.github.io/trace-context).
This specification defines the value and format of the `Headers` used
to propagate the context information needed in distributed traceability scenarios.
The specification
defines how context information is sent and modified between services.
Context information uniquely identifies requests in a distributed system,
and defines a mechanism for adding and propagating provider-specific information.

W3C Trace Context defines the trace context information by means of two fields that are propagated between requests:

- `traceparent`: describes the position of the incoming request with respect to the trace network in a portable format and of pre-defined length. This field shall be mandatory and therefore shall always be reported.

- `tracestate`: extends `traceparent` by allowing vendor-specific data to be added through a set of key-value pairs. This field shall be optional.

To enable the generation of distributed traceability in `W3C Trace Context` format the only thing we have to do is to enable it:

    darwin:
      app-key: darwin
      logging:
        trace-context:
          enabled: true

!!! info "Important"

    If this mode is not enabled, the logging library will automatically propagate `traceparent` and `tracestate` headers as long as they are received in the request, but no special treatment will be performed on them.

    Therefore, the expected behaviour when this mode is disabled will be as follows:

    - If the microservice receives only `B3 headers`, `micrometer-tracing` processes them and generates new `B3 headers` (x-b3-traceid, x-b3-spanid, x-b3-parentspanid, x-b3-sampled) based on those received.

    - If the microservice receives only `W3C headers`, `micrometer-tracing` interprets this as the first request and generates new `B3 headers` (x-b3-traceid, x-b3-spanid, x-b3-parentspanid, x-b3-sampled) where x-b3-traceid and
        x-b3-spanid have the same value. The `W3C headers` are not processed, they are simply propagated keeping the value received in the original request.

    - If the microservice receives `W3C and B3 headers`, `micrometer-tracing` processes and generates traces based on the `B3 headers` received in the request. The `W3C headers` are not processed, they are simply propagated
        keeping the value received in the original request.

From this point on, both `HTTP` microservices and messaging systems will expect to receive `W3C Trace Context: (traceparent, tracestate)` headers, which in turn will propagate those headers. On the other hand, we know that `Darwin` microservices
have always followed the `B3* header standard: (x-b3-traceid, x-b3-spanid, x-b3-parentspanid, x-b3-sampled)` which is automatically managed by `Micrometer`, this implies that if a microservice enables `W3C Trace Context` support, this microservice
will stop interpreting `B3*` headers and therefore will not join the incoming request, nor will it propagate `B3*` headers, so if the request arrives to another microservice that does not have `W3C Trace Context` enabled, it will not be able to join
the current trace. Therefore, a `B3*` header compatibility mechanism has been developed to allow `Darwin` microservices to perform a staged transaction from the `B3` format to the `W3C Trace Context` format. This compatibility mechanism is built in
by enabling `W3C Trace Context` via the `darwin.logging.trace-context.enabled` property, so microservices will get compatibility mode automatically. It is advisable that if the micro does not need this compatibility mode because you only want to
work with the standard `W3C Trace Context`, you should disable it for performance reasons. To disable it, simply use the `darwin.logging.trace-context.enable-compatibility-with-b3` property and initialise it to `false`.

The default built-in compatibility mode works as follows:

- HTTP requests:

    - If a microservice receives headers of type `B3*`, it shall initialise the `TraceContext` from those headers and propagate both `B3*` headers and `W3C TraceContext` headers.

    - If a microservice receives headers of type `W3C TraceContext`, it shall initialise the `TraceContext` from those headers and propagate both `B3*` headers and `W3C TraceContext` headers.

    - If a microservice receives `B3*` and `W3C TraceContext` headers, it shall initialise the `TraceContext` from the `B3*` headers and propagate both `B3*` headers and `W3C TraceContext` headers.

- Messaging requests (kafka topics, activemq, etc):

    - If a micro sends a message to a broker, headers in `W3C TraceContext` format will be generated. These headers are initialised from the information located in the `TraceContext`.

    - If a micro receives a message from a broker, the `TraceContext` shall be initialised from `W3C TraceContext` headers.

This default compatibility mode can be customised by providing the following properties:

- `http-injectors`: Allows to indicate the headers we want to propagate in the invocation to a microservice for `HTTP` requests.

- `messaging-injectors`: Allows us to specify the headers we wish to propagate in the invocation of a messaging service.

- `http-extractors`: Allows to indicate the headers we want to interpret when receiving an `HTTP` request.

- `messaging-extractors`: Allows us to indicate the headers we want to interpret when receiving a messaging service request.

As an example, let's suppose that we want to configure our service so that in `HTTP` requests it only recognises and generates `B3*` headers, but for messaging services it recognises and generates both `B3*` headers and `W3C TraceContext` headers:

    darwin:
      app-key: darwin
      logging:
        trace-context:
          enabled: true
          http-injectors:
            - tracecontext
          messaging-injectors:
            - b3
            - tracecontext
          http-extractors:
            - tracecontext
          messaging-extractors:
            - b3
            - tracecontext

### Configuration Kafka communication protocol

Logging library allows to configure different kind of security protocols for the communications. Currently, Darwin system monitoring offers two kind of Kafka servers: one with `SSL` security activated and another with `PLAINTEXT` protocol.

By default, the library is self-configured to handle all communications against the kafka broker in `SSL` mode. However, in versions prior to 2.11.0 of `Darwin` communications were established via `PLAINTEXT`.

If we need to change this behaviour and revert to `PLAINTEXT` communications we need to set up the following configuration:

    darwin:
      logging:
        kafka:
          properties:
            security.protocol: PLAINTEXT

!!! info "Important"

    When configuring the library in `SSL` mode, the servers and ports corresponding to each environment will be different from the ones that have been configured for `PLAINTEXT`. [In this
    link](https://sanes.atlassian.net/wiki/spaces/SANACLOUD/pages/16816242958/Configuraci+n+de+la+comunicaci+n+de+los+microservicios+con+los+t+picos+de+logging) you can consult the list of servers for each environment, either `SSL` or those provided
    with `PLAINTEXT` support.

In addition, in order to ensure that the different configurations are correct, before validating the connection to Kafka, by default, it is checked that the security of the broker defined and the security protocol chosen for the communications
match. This verification only supports `PLAINTEXT` and `SSL` security protocol.

For allowing to use `SASL_PLAINTEXT` and `SASL_SSL` as security protocol for communications, the verification can be disabled with the `darwin.logging.kafka.protocol-validation.enabled` property:

    darwin:
     logging:
        kafka:
          protocol-validation:
            enabled: false (1)
          server: kafkadarwin.santander.dev.corp:9094
          properties:
            security.protocol: SASL_SSL (2)

1. Disabling verification for `SSL` and `PLAINTEXT` security protocols.

2. Using `SASL_SSL` as security protocol.

This configuration will be valid for `SASL_PLAINTEXT`, we simply have to change `SASL_SSL` security protocol by `SASL_PLAINTEXT` security protocol.

!!! info "Important"

    An invalid configuration will result in all traces being sent to console instead of Kafka, with their respective console format.

### Configuration Headers propagation

To configure logging propagation headers you can use the following example

    darwin:
        core:
            headers:
              enabled: true # Enable/disable propagation headers
              exclude:
                - endpoint: "https://some.api"
                  common: true
                  logging: false
                  security: true
                - endpoint: "https://another.api"
                  common: true
                  logging: true
                  security: true

!!! info "Important"

    When we call to *"https://some.api/\*"* we do not exclude the logging headears to the propagation.

!!! info "Important"

    When we call to *"https://another.api"* we will exclude the logging headers to the propagation.

For more information about the Propagation Headers visit [more information](../darwin-spring-boot-core/README.md#propagation-headers)

## Library use cases and advanced configuration

### How to customize the logging configuration

The logging module exposes a functional API for creating and customising the logging context. By default, Darwin creates a context where all your own logging components are added. It also allows you to define new configuration values, add new
components or modify the ones that are added by default.

LoggingConfig\_ is an interface that represents the configuration of the logging context of an application, which has only one implementation, the DefaultLoggingConfig class. This represents the configuration of the logging context that loads the
application after executing all the autoconfiguration. For the creation of the configuration and the logging context, the LoggingConfig.Builder interface is used, which implements the *Builder* pattern and provides the functional API that allows the
customisation of all its components, besides this interface has a single implementation, DefaultLoggingConfigBuilder. By default, the configuration loaded by the logging module has the same characteristics as in previous versions of the framework.

There are two ways to customise the configuration of the logging context. Modifications can be introduced through the *LoggingConfigCustomizer* functional interface, or, in exceptional cases, a new instance of *LoggingConfig* could be generated
through the logging configuration creation builder, *LoggingConfig.Builder*. The latter option should only be used in case the default Darwin configuration is invalid and all its components have to be replaced by new elements.

#### How to make use of the LoggingConfigCustomizer interface

Darwin creates and pre-configures a LoggingConfig.Builder object from which the logging context will be generated. By default, this object will contain the base Darwin configuration. This configuration can be customised through the use of the
*LoggingConfigCustomizer* functional interface. To make use of this customisation mechanism, it is necessary to declare a bean of type *LoggingConfigCustomizer* where a callback is returned with the modifications to be carried out.

For example, how could you add a new property to the logging configuration through the customizer?

    @Configuration(proxyBeanMethods = false)
    @AutoConfigureBefore(LoggingAutoConfig.class)
    public class LoggingConfigurationCustomization {

        @Bean
        LoggingConfigCustomizer loggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> builder.addProperty("property", "value")
                                                            .addProperty("app", "ms")
                                                            .addRootProperty("root", "value");
        }
    }

All beans of type *LoggingConfigCustomizer* shall be injected during the creation of the *LoggingConfig.Builder* instance and shall be processed to customise the configuration.

The recommended procedure to customise the configuration is to declare a single *Bean* of type *LoggingConfigCustomizer* and add all required modifications.

If, due to project needs, an application has to declare *Beans* of type *LoggingConfigCustomizer*, and at least two of these customisations make modifications to the same component, the configuration generation *builder* will generally only take
into account the changes that are applied first. In order to establish an order and prioritise some customisations over others, Spring's
[*@Order*](https://docs.spring.io/spring-framework/docs/6.0.21/javadoc-api/org/springframework/core/annotation/Order.html) annotation can be used.

Not all operations are affected by the order in which they are performed. To see which actions should be executed with higher priority, see the following [section](#using-the-loggingconfig-builder-interface).

For example, if there is a configuration where two *Bean* of the *LoggingConfigCustomizer* functional interface have been defined, which modify differently the *'TARGET'* attribute of the same appender, how could one of the two customisations of the
appender named *'consoleAppender'* that already exists by default in the configuration be prioritised?

    @Configuration(proxyBeanMethods = false)
    @AutoConfigureBefore(LoggingAutoConfig.class)
    public class LoggingConfigurationCustomization {

        @Bean
        @Order(Ordered.HIGHEST_PRECEDENCE)
        LoggingConfigCustomizer priorityLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {

                ConfigurationBuilder<BuiltConfiguration> configBuilder =
                        ConfigurationBuilderFactory.newConfigurationBuilder();

                AppenderComponentBuilder consoleAppender =
                        configBuilder.newAppender("consoleAppender", "CONSOLE")
                                        .addAttribute("TARGET", ConsoleAppender.Target.SYSTEM_ERR);

                builder.addAppender(consoleAppender);
            };
        }

        @Bean
        @Order(Ordered.LOWEST_PRECEDENCE)
        LoggingConfigCustomizer lowPrecedenceLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {
                ConfigurationBuilder<BuiltConfiguration> configBuilder =
                        ConfigurationBuilderFactory.newConfigurationBuilder();

                AppenderComponentBuilder consoleAppender =
                        configBuilder.newAppender("consoleAppender", "CONSOLE")
                                        .addAttribute("TARGET", ConsoleAppender.Target.SYSTEM_OUT);

                builder.addAppender(consoleAppender);
            };
        }
    }

With this configuration, the effective customisation that would be loaded first would be the customisation that sets the *'ConsoleAppender.Target.SYSTEM\_ERR'* value for the *'TARGET'* attribute of the appender named *'consoleAppender'*, i.e. the
one that has been ordered to have the highest precedence ([*Ordered.HIGHEST\_PRECEDENCE*](https://docs.spring.io/spring-framework/docs/6.0.21/javadoc-api/org/springframework/core/Ordered.html)).

#### How to generate a custom LoggingConfig

The logging library has a default configuration that is loaded if, in the context of the application, there is no other logging configuration defined. In exceptional cases, where the base Darwin configuration is not valid for a certain application,
a new custom configuration could be created by generating a new instance of the LoggingConfig interface through the configuration builder. This would cause that none of the Darwin logging elements would be loaded and therefore, only the components
defined in the new context configuration would be available.

How could we create a new configuration class where to generate a customisation of the logging context through the *LoggingConfig.Builder* interface? We are going to overwrite the default Darwin configuration, generating a new logging context where
we define a logger, named *'customLogger'* , which makes use of a console appender that has a pattern for time stamping, and a logger, named *'mainLogger'*, which makes use of a Kafka appender, named *'kafkaAppender'*, which contains a pattern that
prints in the trace the date and time.

This new configuration would completely replace the default Darwin configuration and will generate the new logging context with all custom elements.

    @Configuration(proxyBeanMethods = false)
    @AutoConfigureBefore(DarwinLoggingConfiguration.class)
    public class CustomLoggingConfiguration {

        @Bean
        public LoggingConfig customLoggerConfig(LoggingConfig.Builder loggingConfigBuilder) {

            ConfigurationBuilder<BuiltConfiguration> configBuilder =
                    ConfigurationBuilderFactory.newConfigurationBuilder();

            AppenderComponentBuilder consoleAppender =
                    configBuilder.newAppender("consoleAppender", "CONSOLE")
                                    .addAttribute("TARGET", ConsoleAppender.Target.SYSTEM_OUT)
                                    .add(configBuilder.newLayout("PATTERN_LAYOUT")
                                    .addAttribute("PATTERN", "%d{HH:mm:ss,SSS}"));

            return loggingConfigBuilder.addProperty("property", "value")
                                .addProperty("app", "ms")
                                .addRootProperty("root", "value")
                                .addLogger(configBuilder.newAsyncLogger("mainLogger", Level.INFO))
                                .addLogger(configBuilder.newAsyncLogger("customLogger", Level.INFO))
                                .addAppender(consoleAppender)
                                .addRefAppenderLogger("customLogger", "consoleAppender")
                                .addDeferAppender(kafkaAppender, null, null, "mainLogger")
                                .build();
        }

        Function<Configuration, Appender> kafkaAppender =
            (Configuration configuration) -> {
                KafkaAppender kafkaAppender = KafkaAppender.newBuilder()
                        .setName("kafkaAppender")
                        .setTopic("kafkaTopic")
                        .setSyncSend(false)
                        .setIgnoreExceptions(false)
                        .setPropertyArray(new Property[0])
                        .setConfiguration(configuration)
                        .setLayout(PatternLayout.newBuilder()
                                                .withPattern("%d{yyyy-MM-dd HH:mm:ss.SSS}")
                                                .build())
                        .build();
                kafkaAppender.start();
                return kafkaAppender;
        };

    }

For more information on the LoggingConfig.Builder interface, see the following [section](#using-the-loggingconfig-builder-interface).

#### Customizing the Kafka connection validator

One of the features of the logging context generation builder is that **it allows appenders to be added in a deferred way**, i.e., these components will be added to the context once it has been created and they will be added in an asynchronous way,
in parallel to the loading of the rest of the autoconfiguration. This is necessary because for certain appenders, they need to validate that the optimal conditions for their operation are met, before being part of the context and, in general, these
checks require some time and could cause delays in the start-up of the application.

Darwin, in its default configuration, adds kafka appenders for activity, functional, frontend, security, alert, root, and for each of the technical loggers. In order to ensure that these elements work, **it is necessary to validate that the kafka
service is accessible**. To perform this task, the *builder* makes use of a connection validator that is injected during the creation of the *LoggingConfig.Builder* instance. This validator is of type `BooleanSupplier` and its instance is qualified
with the name **'kafkaValidator'**. Darwin exposes a *Bean* that satisfies this dependency, but this component can be replaced by other *Bean* of the same type and qualified with the same name, which means that this element can be customised.

To provide a custom implementation of the kafka connection validator, it is as simple as adding a new *Bean* with name **'kafkaValidator'** and type `BooleanSupplier` to the application configuration e.g., to override the default Kafka connection
validation process with a new validator that would not run any checks and always allow kafka appenders to be added, it would be as simple as adding the following configuration:

    @Configuration(proxyBeanMethods = false)
    @AutoConfigureBefore(LoggingAutoConfig.class)
    public class CustomValidatorConfiguration {

        @Bean
        @Qualifier("kafkaValidator")
        public BooleanSupplier customKafkaValidator() {
            return () -> true;
        }

    }

### Using the LoggingConfig-Builder interface

The *LoggingConfig.Builder* interface provides a number of functions that allow customisation of logging configuration properties and components:

- Add a set of system properties.

- Adding loggers.

- Remove an existing logger.

- Referencing an appender to a logger.

- Add/modify an appender.

- Remove an existing appender.

- Adding appenders on a deferred basis.

- Add properties to the logging configuration.

- Add properties to the root logger.

- Create a custom root logger.

- Add a custom *ConfigurationBuilder*.

- Delete the defined root logger.

For the definition of the logging elements, use the Log4j2 component generation builder. This object exposes an API which allows to generate loggers, appenders, layouts, filters, etc. These will be added to the logging configuration through the
*LoggingConfig.Builder* interface.

To obtain a *ConfigurationBuilder* for the creation of the logging components, the following factory must be used:

    ConfigurationBuilder<BuiltConfiguration> configBuilder = ConfigurationBuilderFactory.newConfigurationBuilder();

For more information on how to define logging components from the API exposed by the ConfigurationBuilder class, see the [documentation](https://logging.apache.org/log4j/2.x/manual/customconfig.html).

#### How to add a new Logger to the configuration

It is allowed to add a new logger to the configuration:

    import org.apache.logging.log4j.Level;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilderFactory;

    @Configuration(proxyBeanMethods = false)
    class AddLoggerConfiguration {

        @Bean
        LoggingConfigCustomizer addLoggerLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {
                ConfigurationBuilder<BuiltConfiguration> configBuilder =
                            ConfigurationBuilderFactory.newConfigurationBuilder();

                builder.addLogger(configBuilder.newAsyncLogger("loggerTest", Level.INFO));
            };
        }
    }

Furthermore, it is allowed to associate a logger to an existing appender in the configuration, in order to make use of it.

How could you associate the logger with name "loggerTest" created in the previous example, to a new appender that has as reference "appenderTest", for example:

    import org.apache.logging.log4j.core.appender.ConsoleAppender;
    import org.apache.logging.log4j.core.config.builder.api.AppenderComponentBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilderFactory;

    @Configuration(proxyBeanMethods = false)
    class CustomLoggerConfiguration {

        @Bean
        LoggingConfigCustomizer customLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {
                ConfigurationBuilder<BuiltConfiguration> configBuilder =
                    ConfigurationBuilderFactory.newConfigurationBuilder();

                AppenderComponentBuilder consoleAppender =
                    configBuilder.newAppender("appenderTest", "CONSOLE")
                                       .addAttribute("TARGET", ConsoleAppender.Target.SYSTEM_OUT)
                                       .add(configBuilder.newLayout("PATTERN_LAYOUT")
                                       .addAttribute("PATTERN", "%d{HH:mm:ss,SSS}"));

                builder.addAppender(consoleAppender)
                        .addRefAppenderLogger("loggerTest", "appenderTest");
            };
        }
    }

!!! info "Important"

    In order to add a custom root logger to the configuration, see the following [section](#how-to-add-a-custom-root-logger).

#### How to add/modify an Appender

It is allowed to add/modify an appender in the configuration.

For example, if you want to add an appender with name *'appenderTest'* to the configuration, it would be as simple as:

    import org.apache.logging.log4j.core.appender.ConsoleAppender;
    import org.apache.logging.log4j.core.config.builder.api.AppenderComponentBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilderFactory;

    @Configuration(proxyBeanMethods = false)
    class CustomConfiguration {

        @Bean
        LoggingConfigCustomizer addAppenderLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {
                ConfigurationBuilder<BuiltConfiguration> configBuilder =
                            ConfigurationBuilderFactory.newConfigurationBuilder();

                AppenderComponentBuilder consoleAppender =
                    configBuilder.newAppender("appenderTest", "CONSOLE")
                                    .addAttribute("TARGET", ConsoleAppender.Target.SYSTEM_OUT);

                builder.addAppender(consoleAppender);
            };
        }
    }

!!! info "Important"

    Although this mechanism allows adding any type of appender, it is intended for adding components that do not require prior validation, for example, a console appender. The opposite example would be to add an appender for an
    external service. This element requires to validate that the messaging service is available and this check takes time, so it is more correct to add it in a deferred way and avoid delays at application startup. The *LoggingConfig.Builder* interface
    provides a [mechanism to perform this task](#how-to-add-an-appender-in-a-deferred-way).

To modify an existing appender we must take into account that when an appender is created and added to the logging configuration, it does not allow the modification of any subcomponents. This means that in order to customise them, you have to
regenerate them and apply the required changes. The only requirement here is that each of the new appenders must have the same name as the appender they want to replace.

How could the appender, named 'appenderTest', added in the example above, be modified to add a pattern that prints the hour, minutes and seconds in the trace, it would be as simple as:

    import org.apache.logging.log4j.core.appender.ConsoleAppender;
    import org.apache.logging.log4j.core.config.builder.api.AppenderComponentBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilderFactory;

    @Configuration(proxyBeanMethods = false)
    class CustomConfiguration {

        @Bean
        LoggingConfigCustomizer modifyAppenderLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {
                ConfigurationBuilder<BuiltConfiguration> configBuilder =
                    ConfigurationBuilderFactory.newConfigurationBuilder();

                AppenderComponentBuilder consoleAppender =
                    configBuilder.newAppender("appenderTest", "CONSOLE")
                                    .addAttribute("TARGET", ConsoleAppender.Target.SYSTEM_OUT)
                                    .add(configBuilder.newLayout("PATTERN_LAYOUT")
                                    .addAttribute("PATTERN", "%d{HH:mm:ss,SSS}"));

                builder.addAppender(consoleAppender);
            };
        }
    }

After adding the new appender implementation 'appenderTest', it will replace the original appender.

!!! info "Important"

    If an appender was customised and added several times at different points in the application, only the first customisation that was added to the configuration would be applied. The rest would be discarded.

!!! info "Important"

    Deferred appenders cannot be modified once they have been created.

For more information on the existing appender types and all their configuration parameters, see the [documentation](https://logging.apache.org/log4j/2.x/manual/appenders.html).

#### How to add an Appender in a deferred way

The API exposes a series of methods that allow adding any kind of appender in a deferred way, that is, these components will be added to the logging context once they have been created and validated, and it will be done in an asynchronous way, in
parallel to the instantiation of the rest of the autoconfiguration. This is necessary because for certain appenders, such as the Darwin Kafka appenders, validations are performed prior to their loading, as these checks usually require time that
could cause delays in the application start-up. This way, the loading of this part of the logging configuration is decoupled from the initialisation of the application, making it available to attend tasks.

##### Deferred appender without logger association

It is possible to add a deferred appender without associating it to with some logger. This situation could be interesting for offering a custom deferred appender in the configuration and that it could be associated it to a logger in another part of
the configuration.

    import org.apache.logging.log4j.Level;
    import org.apache.logging.log4j.core.appender.ConsoleAppender;
    import org.apache.logging.log4j.core.config.builder.api.AppenderComponentBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilderFactory;

    @Configuration(proxyBeanMethods = false)
    class CustomConfiguration {

        @Bean
        LoggingConfigCustomizer customDeferAppenderConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {
                 builder.addDeferAppender(kafkaAppender, null, null);
            };
        }

        Function<Configuration, Appender> kafkaAppender =
            (org.apache.logging.log4j.core.config.Configuration configuration) -> {
                // Configure kafka broker, connections properties...
                List<Property> properties = configureKafkaProperties();
                KafkaAppender kafkaAppender = KafkaAppender.newBuilder()
                        .setName("kafkaAppender")
                        .setTopic("kafkaTopic")
                        .setSyncSend(false)
                        .setIgnoreExceptions(false)
                        .setPropertyArray(properties.toArray(new Property[0]))
                        .setConfiguration(configuration)
                        .setLayout(PatternLayout.newBuilder()
                                                .withPattern("%d{HH:mm:ss,SSS}")
                                                .build())
                        .build();
                kafkaAppender.start();
                return kafkaAppender;
        };
    }

This `DeferAppender` can be associated with a logger using the `addRefDeferAppenderLogger` method.

##### Deferred appender with a custom validator

In this case, you want to add the same Kafka deferred appender than before but using a custom validator:

    import org.apache.logging.log4j.Level;
    import org.apache.logging.log4j.core.appender.ConsoleAppender;
    import org.apache.logging.log4j.core.config.builder.api.AppenderComponentBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilderFactory;
    import java.util.function.BooleanSupplier;

    @Configuration(proxyBeanMethods = false)
    class CustomConfiguration {

        @Bean
        LoggingConfigCustomizer customLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {
                 builder.addLogger(configBuilder.newAsyncLogger("logger1", Level.INFO))
                        .addLogger(configBuilder.newAsyncLogger("logger2", Level.DEBUG))
                        .addDeferAppender(kafkaAppender, null, null, this.customValidator(),
                                            "logger1", "logger2");
            };
        }

        private BooleanSupplier customValidator() {
            return () -> // boolean result from any check;
        }

        Function<Configuration, Appender> kafkaAppender =
            (org.apache.logging.log4j.core.config.Configuration configuration) -> {
                // Configure kafka broker, connections properties...
                List<Property> properties = configureKafkaProperties();
                KafkaAppender kafkaAppender = KafkaAppender.newBuilder()
                        .setName("kafkaAppender")
                        .setTopic("kafkaTopic")
                        .setSyncSend(false)
                        .setIgnoreExceptions(false)
                        .setPropertyArray(properties.toArray(new Property[0]))
                        .setConfiguration(configuration)
                        .setLayout(PatternLayout.newBuilder()
                                                .withPattern("%d{HH:mm:ss,SSS}")
                                                .build())
                        .build();
                kafkaAppender.start();
                return kafkaAppender;
        };
    }

The above example can also be done by making use of the [DeferAppender](https://gluon.dev.corp/microservices/docs/darwin-spring-boot/4.3.3-RELEASE/apidocs/com/santander/darwin/logging/DeferAppender.html) class:

    import com.santander.darwin.logging.DeferAppender;
    import org.apache.logging.log4j.Level;

    @Configuration(proxyBeanMethods = false)
    class CustomConfiguration {

        @Bean
        LoggingConfigCustomizer customLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {
                 builder.addLogger(configBuilder.newAsyncLogger("logger1", Level.INFO))
                        .addLogger(configBuilder.newAsyncLogger("logger2", Level.DEBUG))
                        .addDeferAppender(
                                DeferAppender.builder()
                                    .setAppender(kafkaAppender)
                                    .setValidator(this.customValidator())
                                    .setLoggers("logger1", "logger2")
                                    .build()
                        );
            };
        }

        private BooleanSupplier customValidator() {
            return () -> // boolean result from any check;
        }

        Function<Configuration, Appender> kafkaAppender =
            (org.apache.logging.log4j.core.config.Configuration configuration) -> {
                // Configure kafka broker, connections properties...
                List<Property> properties = configureKafkaProperties();
                KafkaAppender kafkaAppender = KafkaAppender.newBuilder()
                        .setName("kafkaAppender")
                        .setTopic("kafkaTopic")
                        .setSyncSend(false)
                        .setIgnoreExceptions(false)
                        .setPropertyArray(properties.toArray(new Property[0]))
                        .setConfiguration(configuration)
                        .setLayout(PatternLayout.newBuilder()
                                                .withPattern("%d{HH:mm:ss,SSS}")
                                                .build())
                        .build();
                kafkaAppender.start();
                return kafkaAppender;
        };
    }

Both examples are equivalent and therefore the loading of the appender will depend on the validation result returned by the custom validator. If the result is positive, the appender is added to the configuration and the association to the defined
loggers is performed.

!!! info "Important"

    Additionally, it is possible to set a log level and a filter to be associated to the appender. In the examples above, both parameters have been left to ***null*** to indicate that these fields do not need to be customised. In
    the case of the *level* parameter, as no value is set, the appender will be created with the log level **ALL**. For the class
    [DeferAppender](https://gluon.dev.corp/microservices/docs/darwin-spring-boot/4.3.3-RELEASE/apidocs/com/santander/darwin/logging/DeferAppender.html), not setting a value for both parameters, ***null*** will be used as
    default value.

!!! info "Important"

    Deferentially created appenders cannot be modified once they have been created.

For more information on existing appender types, see the Log4j2 [documentation](https://logging.apache.org/log4j/2.x/manual/appenders.html).

##### Adding an Appender deferred reference

Finally, you want to add an appender that it already exist in the configuration to a new Logger. How could you associate the Darwin Technical Kafka appender (that it is present in the configuration) to a new custom logger with name *'logger.2'*? An
example code would be the following:

    import com.santander.darwin.logging.DeferAppender;
    import org.apache.logging.log4j.Level;
    import com.santander.darwin.logging.config.LoggingProperties;

    @Configuration(proxyBeanMethods = false)
    class CustomConfiguration {

        @Bean
        LoggingConfigCustomizer customLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {
                 // New DeferAppenderRef for 'KAFKA_TECHNICAL' appender
                 AppenderRef deferAppenderRef = AppenderRef
                    .createAppenderRef(LoggingProperties.KAFKA_TECHNICAL, Level.ERROR, null);
                 builder.addLogger(configBuilder.newAsyncLogger("logger.2", Level.DEBUG))
                        // Adding the AppenderRef for KAFKA_TECHNICAL
                        .addRefAppenderLogger("logger.2", deferAppenderRef);
            };
        }
    }

#### How to make use of a custom *ConfigurationBuilder*

The *builder* allows to add a custom *ConfigurationBuilder* object to the configuration. This custom *ConfigurationBuilder* could be customised and contain any type of element before becoming part of the logging configuration object.

For example, you could create a *ConfigurationBuilder* object and add a custom logger and appender to it:

    import org.apache.logging.log4j.Level;
    import org.apache.logging.log4j.core.appender.ConsoleAppender;
    import org.apache.logging.log4j.core.config.builder.api.AppenderComponentBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilderFactory;

    @Configuration(proxyBeanMethods = false)
    class CustomConfiguration {

        @Bean
        LoggingConfigCustomizer customLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {
                ConfigurationBuilder<BuiltConfiguration> customConfigBuilder =
                    ConfigurationBuilderFactory.newConfigurationBuilder();

                AppenderComponentBuilder consoleAppender =
                    customConfigBuilder.newAppender("appenderName", "CONSOLE")
                                        .addAttribute("TARGET", ConsoleAppender.Target.SYSTEM_OUT)
                                        .add(customConfigBuilder.newLayout("PATTERN_LAYOUT")
                                        .addAttribute("PATTERN", "%d{HH:mm:ss,SSS}"));

                customConfigBuilder.add(customConfigBuilder.newAsyncLogger("loggerName", Level.INFO))
                                   .add(consoleAppender);

                builder.addConfigurationBuilder(customConfigBuilder);
            };
        }
    }

To this custom *customConfigBuilder* object all the default configuration values will be added and the logging context will be created from it.

#### How to add a custom Root Logger

It is possible to create a custom root logger and add it to the configuration.

For example, it might be necessary to create a custom root logger in which you have a console appender with a special pattern:

    import org.apache.logging.log4j.Level;
    import org.apache.logging.log4j.core.appender.ConsoleAppender;
    import org.apache.logging.log4j.core.config.builder.api.AppenderComponentBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilderFactory;

    @Configuration(proxyBeanMethods = false)
    class CustomConfiguration {

        @Bean
        LoggingConfigCustomizer customLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {
                ConfigurationBuilder<BuiltConfiguration> configBuilder =
                    ConfigurationBuilderFactory.newConfigurationBuilder();

                AppenderComponentBuilder consoleAppender =
                    configBuilder.newAppender("appenderName", "CONSOLE")
                                    .addAttribute("TARGET", ConsoleAppender.Target.SYSTEM_OUT)
                                    .add(configBuilder.newLayout("PATTERN_LAYOUT")
                                    .addAttribute("PATTERN", "%d{HH:mm:ss,SSS}"));

                RootLoggerComponentBuilder rootLogger =
                    configBuilder.newAsyncRootLogger(Level.INFO)
                                 .add(configBuilder.newAppenderRef("appenderName"));

                builder.createRootLogger(rootLogger)
                       .addAppender(consoleAppender);
            };
        }
    }

!!! info "Important"

    If the root logger is customised at several different points in the application, the implementation that is applied first will be the one used for the generation of the logging configuration. The rest will be discarded.

#### How to create different logging configurations depending on the profile

For an application it might be necessary to have different logging configurations depending on the environment it is running in. For example, you might have a different configuration of loggers and appenders between the default configuration and a
test environment. This profile management is possible thanks to the use of the *LoggingConfigCustomizer* interface as a bean and the definition of Spring's
[*@Profile*](https://docs.spring.io/spring-framework/docs/6.0.21/javadoc-api/org/springframework/context/annotation/Profile.html) annotation.

How to define a configuration that is only loaded when the application is running in test mode, it would be as simple as:

    import org.apache.logging.log4j.Level;
    import org.apache.logging.log4j.core.appender.ConsoleAppender;
    import org.apache.logging.log4j.core.config.builder.api.AppenderComponentBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilderFactory;

    import static com.santander.darwin.logging.config.LoggingProperties.CONSOLE_TECHNICAL;
    import static com.santander.darwin.logging.config.LoggingProperties.CONSOLE_FUNCTIONAL;
    import static com.santander.darwin.logging.config.LoggingProperties.CONSOLE_TECHNICAL;
    import static com.santander.darwin.logging.config.LoggingProperties.CONSOLE_SECURITY;
    import static com.santander.darwin.logging.config.DarwinLoggingConfiguration.DarwinLoggerName.FUNCTIONAL;
    import static com.santander.darwin.logging.config.DarwinLoggingConfiguration.DarwinLoggerName.SECURITY;

    @Configuration(proxyBeanMethods = false)
    class CustomConfiguration {

        protected static final String TARGET = "target";
        protected static final String PATTERN = "pattern";
        protected static final String PATTERN_LAYOUT = "PatternLayout";

        @Bean
        @Profile("test")
        LoggingConfigCustomizer testLoggingConfigCustomizer(LoggingProperties loggingProperties) {
            return (LoggingConfig.Builder builder) -> {

                ConfigurationBuilder<BuiltConfiguration> configBuilder =
                    ConfigurationBuilderFactory.newConfigurationBuilder();

                String technicalPattern = loggingProperties.getPattern().getTechnical();
                AppenderComponentBuilder consoleTechnicalBuilder =
                    configBuilder.newAppender(CONSOLE_TECHNICAL, CONSOLE)
                                    .addAttribute(TARGET, ConsoleAppender.Target.SYSTEM_OUT)
                                    .add(configBuilder.newLayout(PATTERN_LAYOUT)
                                    .addAttribute(PATTERN, technicalPattern));

                String functionalPattern = loggingProperties.getPattern().getSecurity();
                AppenderComponentBuilder consoleFunBuilder =
                    configBuilder.newAppender(CONSOLE_FUNCTIONAL, CONSOLE)
                                    .addAttribute(TARGET, ConsoleAppender.Target.SYSTEM_OUT)
                                    .add(configBuilder.newLayout(PATTERN_LAYOUT)
                                    .addAttribute(PATTERN, functionalPattern));

                String securityPattern = loggingProperties.getPattern().getSecurity();
                AppenderComponentBuilder consoleSecurityBuilder =
                    configBuilder.newAppender(CONSOLE_SECURITY, CONSOLE)
                                    .addAttribute(TARGET, ConsoleAppender.Target.SYSTEM_OUT)
                                    .add(configBuilder.newLayout(PATTERN_LAYOUT)
                                    .addAttribute(PATTERN, securityPattern));

                RootLoggerComponentBuilder rootLogger =
                    configBuilder.newAsyncRootLogger(Level.INFO)
                                 .add(configBuilder.newAppenderRef(CONSOLE_TECHNICAL));

                builder.createRootLogger(rootLogger)
                        .addAppender(consoleTechnicalBuilder)
                        .addAppender(consoleFunBuilder)
                        .addAppender(consoleSecurityBuilder)
                        .addRefAppenderLogger(FUNCTIONAL.getName(), CONSOLE_FUNCTIONAL)
                        .addRefAppenderLogger(SECURITY.getName(), CONSOLE_SECURITY);
            };
        }
    }

In this configuration, the technical console appender is updated to use the same pattern that the Kafka appender would use, a console appender is added for the functional logger and another console appender for the security logger. In addition, a
new root logger is created to make use of the technical console appender.

#### How to customize the Console Appender defined by default

To replace the default console appenders in each of the Darwin loggers with a custom configuration, simply use the LoggingConfigCustomizer as Bean.

        @Bean
        LoggingConfigCustomizer customizeConsoleAppenders(LoggingProperties loggingProperties) {
            return (LoggingConfig.Builder builder) -> {

    }

### How to generate traces manually

#### How to generate FATAL level traces

To generate a trace within the system that has a `FATAL` log level, it is necessary to use the `com.santander.darwin.logging.logger.ExtendedLogger` class, building it in a similar way as the `logger` of SLF4J and invoking the `fatal` method once it
is built:

    ExtendedLogger extendedLogger = new ExtendedLogger(this)

    public void aCriticalMethod(){
        try{
            //Some critical code
        }catch(Exception ex){
            extendedLogger.fatal("The most critical part of the application failed.", ex);
        }
    }

The `ExtendedLogger` provides the same methods as the `Logger` interface, so you can send either rich traces or the trace with an exception that will be displayed next to your stack trace.

#### How to generate functional traces

The functional traces allow four different parameters, and it is possible to use the different combination of these:

- An optional String traceLog that will be replaced by the URL of the current context in case it is not provided.
- A Map&lt;String, Object&gt; businessLogMap that will include key information for business.
- A List&lt;String&gt; sensibleFields that allows to hide information given in the businessLogMap.
- A Map&lt;String, Object&gt; functionalCustomLog that can include extra information.

##### Non-reactive environments

To write a functional type trace, we will have to resort to the `FunctionalLogHelper` class and invoke the `log` method supplying it with the trace we want to be displayed and a map with the data we want to be included in the businessLog field, as
an example:

        Map<String, Object> businessLogMap = new HashMap<>();
        businessLogMap.put("function", "checkCredit");
        businessLogMap.put("description", "Checking the credit card status.");
        FunctionalLogHelper.log("No credit card found.", businessLogMap);

!!! note

The traceLog string is optional and in case it is not provided, the URL from the context will be taken.

The result of this log will be as follows:

##### Reactive environments

In order to use this functionality in `Reactive` environments, the `DARWIN` architecture provides the `FunctionalReactiveLogHelper` class which is functionally equivalent to `FunctionalLogHelper`. The reactive implementation expose the `trace(…​)`

Here an example the use of method:

            logMap.put("description", "Second Content Check");
            return Mono.justOrEmpty("Hello World!")
                    .doOnEach(FunctionalReactiveLogHelper.trace("Checking functional log", logMap));

#### How to generate activity traces

These kind of traces are only enabled for the ***NotWeb*** environment, and the reason is that in `Servlet and/or Reactive` environments with automatic generation of activity traces, most of the information is filled from the `Headers HTTP`, but as
these are not available in this kind of environments, it is necessary to provide `Darwin` with the necessary mechanisms to supply this `gap`. With this objective in mind, the `LoggingContext` class is provided so that the user can manually fill in
all those fields that are of interest to the application.

The class is implemented with the `Builder` pattern making it immutable. In addition, all fields will be initialised to `Null String` except the `InputTimeStamp` which is initialised with the `timeStamp` of the creation of this object.

    package com.santander.darwin.logging.service;

    import lombok.Builder;
    import lombok.Getter;
    import java.time.Instant;

    @Builder(toBuilder = true)
    @Getter
    public class LoggingContext {
        private String sessionId; // COMMON_JSON_PATTERN
        private String userAgent; // COMMON_JSON_PATTERN
        private String appInit; // COMMON_JSON_PATTERN
        @Builder.Default
        private String inputTimeStamp = DateTimeFormatter.ISO_INSTANT.format(Instant.now().truncatedTo(ChronoUnit.MILLIS)); // ACTIVITY_JSON_PATTERN
        private String method; // ACTIVITY_JSON_PATTERN
        private String clientId; // ACTIVITY_JSON_PATTERN
        private String URL; // ACTIVITY_JSON_PATTERN
        private String returnCode; // ACTIVITY_JSON_PATTERN
        private String errorOccurred; // ACTIVITY_JSON_PATTERN
        private String channel; // ACTIVITY_JSON_PATTERN
        private String log; // ACTIVITY_PATTERN
        @Builder.Default
        private Map<String, String> customActivityLog = new HashMap<String, String>();

    }

##### Non-reactive environments

Now, with this `Bean` we will be able to generate activity traces.

There will be two models based on the field `log`:

1. When the field log doesn't have any value:

        LoggingContext loggingContext = LoggingContext.builder()
        .appInit("foo").returnCode("0").errorOccurred("false").method("main").channel("INT").build(); // (1)

        loggingService.log(loggingContext); // (2)

    1. We create an object of type `LoggingContext` with the activity trace information.

    2. The activity trace is generated. The `log` field of the trace will contain the name of the URL present in the LoggingContext.

2. When the field log does have a specified value:

        LoggingContext loggingContext = LoggingContext.builder()
        .appInit("foo").log("JobListener.afterJob").returnCode("0").errorOccurred("false").method("main").channel("INT").build(); // (1)

        loggingService.log(loggingContext); // (2)

    1. We create an object of type `LoggingContext` with the activity trace information.

    2. The activity trace is generated. The `log` field of the trace will contain `JobListener.afterJob`, which is the same value that's declared in the LoggingContext builder.

##### Obfuscate Functional data

Thanks to the `ObfuscateFunctionalLog` annotation, it is possible to hide sensible information on the input and the output fields inside Functional traces when these are generated by the automatic instrumentation.

The annotation allow us to mark any controller method annotated with `@GetMapping`, `@PostMapping`, `@PatchMapping`, `@PutMapping`, and `@RequestMapping` inside a `@RestController` class. Also, it is possible to use it at the top class level in
order to set a common sensible fields for all the controller methods (`@GetMapping`, `@PostMapping`, `@PatchMapping`, `@PutMapping`, and `@RequestMapping`) defined in the class (`@RestController`). If some endpoints defined in the rest controller
class is present in the list of the functional logging endpoints (`darwin.logging.functional.logged-endpoints`), and the annotation is used at the top class level or for marking the controller method, when the functional trace is generated, both the
input and output will be processed and the sensible fields will be hidden. In order to set the sensible fields, the annotation (`@ObfuscateFunctionalLog`) provides two parameters (sensibleInput and sensibleOutput) in order to define the sensible
fields to hide.

Developer can use two ways in order to define the information that have to be hidden:

1. Using accurate expressions through [Jayway JsonPath specification](https://github.com/json-path/JsonPath#getting-started).

2. Simple references of the fields in order to hide all their appearances.

!!! note

    The annotation `@ObfuscateFunctionalLog` can be used in both `Reactive` web applications and `Servlet` web applications.

**Example of the `ObfuscateFunctionalLog` annotation at the top class level.**

First, the path has to be defined inside the list of the functional logged endpoints as follows:

    darwin:
      logging:
        functional:
          logged-endpoints:
            - /top-level-class/sensible
            - /top-level-class/get-sensible

After, the annotation is used for marking the top class of the rest controller component. In this case, both the controller methods manage endpoints that they are defined in the list of functional endpoints, so both of them generate functional
traces and their input and output fields are sensitised.

    import com.santander.darwin.logging.annotation.ObfuscateFunctionalLog;
    import org.springframework.web.bind.annotation.RequestParam;
    import org.springframework.web.bind.annotation.RequestMapping;
    import org.springframework.web.bind.annotation.RestController;

    @RestController
    @RequestMapping("/top-level-class")
    @ObfuscateFunctionalLog(sensibleInput = {"$.name"}, sensibleOutput = {"$.name", "$.idAccount"})
    public class ApiController {

        @PostMapping(value = "/sensible")
        public User postSensible(
                @RequestBody User user, @RequestParam int newAccount) {
            String name = user.getName();
            return new User(name, newAccount);
        }

        @PostMapping(value = "/get-sensible")
        public User getSensibleData() {
            return new User("Rose", 54321);
        }

    }

    @Data
    @AllArgsConstructor
    public static class User {

        private String name;

        private int idAccount;
    }

For the *postSensible()* method, the input data inside its functional trace will have this form:

    {
      "name": "****",
      "accountNumber": 12345
    }

And the output field in the functional trace will have the following form:

    {
      "name": "****",
      "accountNumber": "****"
    }

### Baggage

In distributed systems, traceability is carried out thanks to the propagation of fields between services that are connected, mainly with *tradeId* and *spanId*. To maintain traceability consistency, use is made of a context where these fields are
maintained, these are called `Baggage`.

Darwin, through the integration of **Micrometer Tracing**, allows the aggregation of new `Baggages` within the traceability context. These new fields can be configured in such a way that their values will be present and synchronised in the MDC, and
will be propagated as headers in outgoing requests to other services.

#### Header propagation

**Propagation** is the method by which it is ensured that all data of an activity originating from the same starting point are collected together in a single trace. This is made possible through the use of a propagation context to hold all this
information. Through the use of `Baggage fields`, these properties can be passed along with the request data. A `Baggage` may be defined, allowing their value to be obtained from incoming HTTP headers, and their value to be propagated as an outgoing
HTTP header to an external service.

##### Configure via properties

Baggage fields that do not require special configuration for propagate from/to headers may be configured through the use of the following property: `management.tracing.baggage.remote-fields`. This is a list of fields that are referenced the same
in-process as it is on the wire. For example, with this config the field "x-vcap-request-id" would be set as-is including the prefix.

    management:
      tracing:
        baggage:
          remote-fields:
            - x-vcap-request-id

This setting will cause the creation of one `Baggage` that will be automatically added to the Baggage context from header value, and then propagated as header on the wire.

!!! info "Important"

    Adding too many entries in the MDC can have a very negative impact on the performance of the application!

##### Configure via customizer

Apart from the use of properties for the creation of Baggage fields, we can also do it programmatically through the use of a ***Bean* that implements the `BaggagePropagationCustomizer` interface**. Doing such a configuration through code instead of
using properties give us some advantages:

- **Customisation of the header's name** for **remote** Baggage fields.

- It also allows to **create local Baggage fields**. These fields are not created from a Http header and aren't propagated on the wire.

!!! note

    In previous versions local Baggage fields were also configurable via properties, since Spring Boot 3.0.x this is only allowed via customizer.

If you want to add a configuration where you create three `Baggage` fields:

- ***local***: will be used locally and will not be managed as HTTP header.

- ***remote***: that will be used remotely and use the same name for the header.

- ***customRemote***: will be used remotely but using "x-vcap-request-id" as the name of the header.

<!-- -->

    import brave.baggage.BaggageField;
    import brave.baggage.BaggagePropagation;
    import brave.baggage.BaggagePropagationCustomizer;

    import static brave.baggage.BaggagePropagationConfig.SingleBaggageField;

    @Configuration(proxyBeanMethods = false)
    public class BaggageFieldsConfig {

        protected static final BaggageField REMOTE = BaggageField.create("remote");

        protected static final BaggageField CUSTOM_REMOTE = BaggageField.create("customRemote");

        protected static final BaggageField LOCAL = BaggageField.create("local");

        @Bean
        BaggagePropagationCustomizer propagationBaggage() {
            return
                (BaggagePropagation.FactoryBuilder factoryBuilder) -> {
                    factoryBuilder
                    .add(SingleBaggageField.remote(REMOTE))
                    .add(SingleBaggageField.remote(
                            SingleBaggageField.newBuilder(CUSTOM_REMOTE).addKeyName("x-vcap-request-id")
                            .build()))
                    .add(SingleBaggageField.local(LOCAL));
                };
        }
    }

!!! note

    All remote `Baggage` header names will be propagated using the lower case string.

#### Correlation with MDC

Spring and Micrometer, through the use of its instrumentation and through the use of the `Baggage fields`, simplifies the interaction with the MDC context, allowing the developer to forget about the synchronisation of the MDC context.

Since MDC is associated with the thread, and in multi-threaded applications, where the main execution *thread* can be changed or where tasks are executed asynchronously, it is necessary to have a management that ensures that the MDC context is
copied from one thread to another. If the MDC is used directly, synchronisation mechanisms should be implemented to ensure alignment with the content of the contexts between several threads of the same execution. For single-threaded environments,
the use of MDC is straightforward and would not require any special management.

A `Baggage` and its content, apart from being acquired and propagated via HTTP headers, can be configured to be value-added and synchronised with the MDC. There are several update and synchronisation policies and, depending on the different needs,
they can be configured in one way or another. There are two ways to configure the application to correlate its content with the context.

##### Configure via properties

You can achieve this through the use of the `management.tracing.baggage.correlation.fields` property. It allows you to define a list with the names of the `Baggage fields`, both local and remote, to be added as fields to the MDC.

This solution configures a synchronisation policy to update the Baggage value in the MDC **immediately**. This alignment between the MDC fields and the updated values of the `Baggages` occurs when an update of the traceability context is performed.

For example, to configure the previous `Baggage` "x-vcap-request-id" to have its value added to the MDC, you would have to define the following settings:

    management:
      tracing:
        baggage:
          remote-fields:
            - x-vcap-request-id
          correlation:
            fields:
              - x-vcap-request-id

##### Configure via customizer

Alternatively to the definition of the properties, the configuration could have been done programmatically through the use of a ***Bean* that implements the `CorrelationScopeCustomizer` interface**. Furthermore, this configuration allows customising
the update policy of the `Baggage` values with the MDC. If a `Baggage` is added to the **CorrelationScopeDecorator** decorator by setting it to ***flushOnUpdate***, each time its value is updated, it will be synchronised with its corresponding field
in the MDC. Otherwise, it'll be synchronised lazily.

If you want to add a configuration where you create three `Baggage` fields:

- ***remote***: remote Baggage field with immediate synchronisation.

- ***local***: local Baggage field with immediate synchronisation.

- ***lazy***: local Baggage field with lazy synchronisation.

<!-- -->

    import brave.baggage.BaggageField;
    import brave.baggage.BaggagePropagation;
    import brave.baggage.BaggagePropagationCustomizer;

    import static brave.baggage.BaggagePropagationConfig.SingleBaggageField;

    @Configuration(proxyBeanMethods = false)
    public class BaggageFieldsConfig {

        protected static final BaggageField REMOTE = BaggageField.create("remote");

        protected static final BaggageField LOCAL = BaggageField.create("local");

        protected static final BaggageField LAZY = BaggageField.create("lazy");

        @Bean
        BaggagePropagationCustomizer propagationBaggage() {
            return
                (BaggagePropagation.FactoryBuilder factoryBuilder) -> {
                    factoryBuilder.add(SingleBaggageField.remote(REMOTE));
                    factoryBuilder.add(SingleBaggageField.local(LOCAL));
                    factoryBuilder.add(SingleBaggageField.local(LAZY));
                };
        }

        @Bean
        CorrelationScopeCustomizer flushToMDCOnUpdate() {
            return
                (CorrelationScopeDecorator.Builder builder) -> {
                    builder.add(SingleCorrelationField.newBuilder(REMOTE).flushOnUpdate().build());
                    builder.add(SingleCorrelationField.newBuilder(LOCAL).flushOnUpdate().build());
                    builder.add(SingleCorrelationField.newBuilder(LAZY).build());
                };
        }
    }

!!! info "Important"

    Adding too many entries in the MDC can have a very negative impact on the performance of the application!

#### Baggage Usage

The **Baggage fields represent the traceability context information**. They are created and customised through the application configuration as described in the [Header propagation](#header-propagation) and [Correlation with
MDC](#correlation-with-mdc) sections. Once these have been added to the propagation context, the tracking of an execution flow has been initiated and a traceability context exists, they can be accessed and modified at any point in the application
through the `BaggageField` class:

    import brave.baggage.BaggageField;

    public class SomeService {

        public void someThingService(String remote, String local) {
            BaggageField.getByName("remote").updateValue(remote);
            BaggageField.getByName("local").updateValue(local);
        }
    }

For more information on the use of `Baggage`, see the [Brave](https://github.com/openzipkin/brave/blob/master/brave/README.md#baggage) documentation.

#### Manual instrumentation

Spring and Micrometer base the use of all this functionality on application instrumentation. The libraries are self-configuring depending on the scope and type of application to expose a series of components that orchestrate the operation and allow
the execution flow to be mapped.

In the case of **Web applications**:

- For `Servlet` applications, they configure the entire tracing infrastructure and adds a web filter that takes care of processing incoming HTTP requests and generating the basic tracing units that will be propagated to allow the tracing of the
    execution flow by each of the running services.

- For `Reactive` applications, it depends on which instrumentation mode is configured. If `automatic mode` is enabled it works like Servlet applications. But if `limited/manual mode` is enabled there are some restrictions to work with `Baggage`
    fields: as they are related to TraceContext, you need to use an operator that retrieve this information from Reactor Context. These are ***tap()*** and ***handle()***:

        public class SomeService {
                public Mono<String> hello(String value1, String value2) {
                    return Mono.just("Hello!")
                    .tap(() -> new DefaultSignalListener<>() {
                        @Override
                        public void doOnNext(String value) throws Throwable {
                            BaggageField.getByName("remote").updateValue(value1);
                        }
                    })
                    .handle((content, sink) -> {
                        BaggageField.getByName("local").updateValue(value2);
                        sink.next(content);
                    });
                }
        }

Finally, in the case of `non-web applications`, traceability functions are to be added to the execution of a process and its execution flow is to be tracked, it is necessary to manually create the monitoring elements. An example would be:

    import brave.Span;
    import brave.Tracer;

    public class SomeService {

        public void someThingService(String remote, String local) {

            Tracer tracer = Tracing.currentTracer();
            Span span = tracer.nextSpan().name("example").start();

            try (SpanInScope ws = tracer.withSpanInScope(span)) {

                BaggageField.getByName("remote").updateValue(remote);
                BaggageField.getByName("local").updateValue(local);
                return callExternalService();
            }
            finally {
                // always finish the span
                span.finish();
            }
        }
    }

The ***nextSpan()*** method will generate the basic elements and create a traceability context for execution. Once all this structure is generated, it will be possible to make effective use of the configured `Baggage` fields, allowing to interact
with the MDC and propagating the headers to the external services. Once the code block to be traced is finished, it is necessary to finalise the traceability element.

For more information on how to implement tracing manually, see the [Micrometer Tracing](https://micrometer.io/docs/tracing#_using_micrometer_tracing_directly) documentation.

### How to add fields in log patterns

Currently, there are three log patterns `GLOBAL`, `GLUONLOG` and `SPAIN` to which new fields can be added. We can define this format through the `logging.pattern.format` property. See [here](#pattern-configuration).

!!! info "Important"

    Old format (**SPAIN format**) will be deprecated in the following version.

The patterns that the loggers already have predefined can be modified through configuration (See [custom-pattern properties](#pattern-configuration)). This property overrides the pattern completely, so the process to follow would be:

1. Get the pattern to modify from [section (3.3.x)](#pattern-configuration)

2. Add the new field in the pattern.

#### Example: custom security-pattern

Now we are going to customize the **security pattern** to add new custom fields and fill in their values from the runtime data.

The goal is to add field **customizedField** in the security pattern with GLOBAL format. We must define the `darwin.logging.pattern.security` property. We take the pattern from [Security pattern](#security-pattern) and modify it by adding the new
field with the next format:

- Retrieved value from a property: **"customizedField":"${customizedField}"**

- Retrieved value from a baggageField or from the MDC: **"customizedField":"%X{customizedField}"**

<!-- -->

    darwin:
      logging:
        pattern:
          security: {"customLog":{"customizedField":"%X{customizedField}"},"logType":"security","securityAttributes":%X{securityAttributes},"result":{"resultCode":"%X{secResultCode}"} %ex{0}%n

#### Add BaggageField to trace

If the field we want to add, it is going to be updated through a baggageField, we have two options for its value to be propagated to the logger:

- Read from a HTTP Header (remote Baggage field)

- Generated value in the application (local Baggage field)

In both cases it will be necessary to create a **Bean** of type `CorrelationScopeCustomizer` so that the value is propagated correctly and it is always available in the MDC for printing its value in the trace fields:

    import brave.baggage.BaggageField;
    import brave.baggage.CorrelationScopeConfig;
    import brave.baggage.CorrelationScopeCustomizer;
    import brave.baggage.CorrelationScopeDecorator;
    import org.springframework.context.annotation.Bean;
    import org.springframework.context.annotation.Configuration;

    @Configuration(proxyBeanMethods = false)
    public class LoggingConfigurationCustomization {
        BaggageField customizedField = BaggageField.create("customizedField");

        @Bean
        CorrelationScopeCustomizer correlationScopeCustomizedField() {
            return (CorrelationScopeDecorator.Builder builder) -> builder
                    .add(CorrelationScopeConfig.SingleCorrelationField.newBuilder(customizedField).flushOnUpdate()
                            .build());
        }
    }

!!! note

    In order to get more information, look at [Correlation with the MDC](#correlation-with-mdc) section.

##### Read from an HTTP Header

Simply add the following property. Spring will automatically generate a BaggageField named **customizedField** that will take its value from a header that has as its name the reference that has been set in remote-field (customizedField).

    management:
      tracing:
        baggage:
          remote-fields:
            - customizedField

##### Generated value in the application

We can do it by code:

    import brave.baggage.BaggageField;
    import brave.baggage.BaggagePropagation;
    import brave.baggage.BaggagePropagationConfig;
    import brave.baggage.BaggagePropagationCustomizer;
    import org.springframework.context.annotation.Bean;
    import org.springframework.context.annotation.Configuration;

    @Configuration(proxyBeanMethods = false)
    public class LoggingConfigurationCustomization {

        BaggageField customizedField = BaggageField.create("customizedField");

        @Bean
        BaggagePropagationCustomizer baggagePropagationCustomizedField() {
            return (BaggagePropagation.FactoryBuilder factoryBuilder) -> factoryBuilder
                    .add(BaggagePropagationConfig.SingleBaggageField.local(customizedField));
        }
    }

!!! note

    This way, it is established that the BaggageField created will only be used locally at execution and that its value can be updated through the **tracing context** at any time.

Once created (through properties or code), we can update the value of the baggageField as follows:

    ...
    TraceContext traceContext = tracer.currentSpan().context(); (1)
    BaggageField.getByName(traceContext, "customizedField").updateValue("customizedValue");
    ...

1. **tracer** is a Bean of type `brave.Tracer` provided by the **io.zipkin.brave:Brave** library.

### Automatic trace customization

The logging library creates and configures a filter for web requests that generates activity and functional traces automatically.

#### Activity traces

For the automatic generation of activity traces, use is made of a component that implements the `ActivityLogger` / `ReactiveActivityLogger` interface. This interface defines a `log` method that has as parameters the status of the HTTP request, the
object representing the request and possible custom values for ActivityLog.

By default, Darwin satisfies that implementation by generating a base version for that component. In case a more specific `ActivityLogger` is needed, it can be customised and added to the configuration in a simple way.

The activity trace generation pattern is updated:

    darwin:
      logging:
        pattern:
          activity: '%X{field1} - %X{field2} - %X{extended}'

We can also replace the implementations provided by the default `ActivityLoggerImpl` / `ReactiveActivityLoggerImpl` architecture with custom ones:

##### Customize a ReactiveActivityLogger in a Reactive application

The `ReactiveActivityLogger` is then implemented in such a way that the values corresponding to the fields present in the new pattern are added to the MDC:

    import com.santander.darwin.logging.logger.reactive.ReactiveActivityLogger;
    import org.slf4j.MDC;
    import org.springframework.http.server.reactive.ServerHttpRequest;
    import reactor.core.publisher.Mono;

    import static com.santander.darwin.logging.config.DarwinLoggingConfiguration.DarwinLoggerName.ACTIVITY;

    public class CustomActivityLoggerImpl implements ReactiveActivityLogger {

        private static final Logger LOGGER = LoggerFactory.getLogger(ACTIVITY);

        @Override
        public Mono<Void> log(HttpStatus httpStatus, ServerHttpRequest request, Map<String, String> customValues) {

            MDC.put("field1", "value1");
            MDC.put("field2", "value2");
            MDC.put("extended", "value3");

            if (LOGGER.isInfoEnabled()) {
                LOGGER.info("Custom Activity trace: httpStatus: '{}'",
                                    String.valueOf(httpStatus.value()));
            }

            MDC.remove("field1");
            MDC.remove("field2");
            MDC.remove("extended");

            // This is useful in case we need to execute blocking code
            return Mono.empty();
        }
    }

Finally, such a component will be instantiated via the `Reactive` environment configuration and automatically injected into the logging filter:

    import com.santander.darwin.logging.config.LoggingReactiveAutoConfig;
    import com.santander.darwin.logging.logger.web.ActivityLogger;

    @Configuration(proxyBeanMethods = false)
    public class ReactiveLoggingConfig {

        @Bean
        public ReactiveActivityLogger customActivityLogger() {
            return new CustomActivityLoggerImpl();
        }
    }

##### Customize a ActivityLogger in a Servlet application

For `Servlet` environments, it is necessary to define an `ActivityLogger`.

An example of customisation of the `ActivityLogger` could be an implementation that makes use of the `LoggerFactory.getLogger(ACTIVITY)` along with a custom activity trace generation pattern. To satisfy the fields of that pattern, they should be
added to the MDC together with their values:

The `ActivityLogger` is then implemented in such a way that the values corresponding to the fields present in the new pattern are added to the MDC:

    import com.santander.darwin.logging.logger.web.ActivityLogger;
    import org.slf4j.MDC;
    import jakarta.servlet.http.HttpServletRequest;

    import static com.santander.darwin.logging.config.DarwinLoggingConfiguration.DarwinLoggerName.ACTIVITY;

    public class CustomActivityLoggerImpl implements ActivityLogger {

        private static final Logger LOGGER = LoggerFactory.getLogger(ACTIVITY);

        @Override
        public void log(HttpStatus httpStatus, HttpServletRequest request, Map<String, String> customValues) {

            MDC.put("field1","value1");
            MDC.put("field2","value2");
            MDC.put("extended","extended-data");

            if (LOGGER.isInfoEnabled()) {
                LOGGER.info("Custom Activity trace: httpStatus: '{}'",
                                    String.valueOf(httpStatus.value()));
            }

            MDC.remove("field1");
            MDC.remove("field2");
            MDC.remove("extended");
        }
    }

Finally, such a component will be instantiated via the `Servlet` environment configuration and automatically injected into the logging filter:

    import com.santander.darwin.logging.config.LoggingAutoConfig;
    import com.santander.darwin.logging.logger.web.ActivityLogger;

    @Configuration(proxyBeanMethods = false)
    public class ServletLoggingConfig {

        @Bean
        public ActivityLogger customActivityLogger() {
            return new CustomActivityLoggerImpl();
        }
    }

!!! note

    For more information on creating and customising traceability components, see the documentation about [configuration](#how-to-customize-the-logging-configuration) of logging.

#### Functional traces

For the automatic generation of functional traces, a component implementing the `FunctionalLogger` / `ReactiveFunctionalLogger` interface is used. This interface defines a `log` method that has as parameters the content of the request body, the
content of the response body, and the object representing the request.

First, the functional trace generation pattern is updated:

    darwin:
      logging:
        pattern:
          functional: '%X{field1} - %X{extended} - \"input\": %X{input} - \"output\":%X{output}'

By default, Darwin satisfies that implementation by generating a base version for that component. In case a more specific `FunctionalLogger` is needed, new implementations can be added to coexist with the architecture implementation or replace the
one added by the default architecture.

##### Customize a ReactiveFunctionalLogger in a Reactive application

For `Reactive` environments, it is necessary to define a `ReactiveFunctionalLogger`.

An example of customisation of the `ReactiveFunctionalLogger` could be an implementation that makes use of the `LoggerFactory.getLogger(FUNCTIONAL)` together with a custom functional trace generation pattern. To satisfy the fields of that pattern,
they should be added to the MDC together with their values.

The `ReactiveFunctionalLogger` is then implemented in such a way that the values corresponding to the fields present in the new pattern are added to the MDC:

    import com.santander.darwin.logging.logger.web.FunctionalLogger;
    import org.slf4j.MDC;
    import org.springframework.http.server.reactive.ServerHttpRequest;

    import static com.santander.darwin.logging.config.DarwinLoggingConfiguration.DarwinLoggerName.FUNCTIONAL;

    public class CustomFunctionalLoggerImpl implements ReactiveFunctionalLogger {

        private static final Logger LOGGER = LoggerFactory.getLogger(FUNCTIONAL);

        @Override
        public Mono<Void> log(String input, String output, ServerHttpRequest request, DarwinContext darwinContext) {

            String path = request.getPath().pathWithinApplication().toString();

            MDC.put("field1", "value1");
            MDC.put("extended", "extended-data");

            MDC.put("input", input);
            MDC.put("output", output);

            if (LOGGER.isInfoEnabled()) {
                LOGGER.info("Custom Functional trace: endpoint: '{}'", path);
            }

            MDC.remove("field1");
            MDC.remove("extended");
            MDC.remove("input");
            MDC.remove("output");

            // This is useful in case we need to execute blocking code
            return Mono.empty();
        }

        @Override
        public boolean isLoggableEndpoint(ServerHttpRequest request) {
            // If we want to limit the conditions under which the functional
            // trace is performed, we can use this method.
            return true;
        }

    }

Finally, such component will be instantiated via the `Reactive` environment configuration, and to be automatically injected into the logging filter **this bean have to be named "functionalLogger"**:

!!! info "Important"

    If the name of the created bean is `functionalLogger`, the bean provided by Darwin will be substituted, if the name is different, both the added bean and the one provided by Darwin will be executed.

        import com.santander.darwin.logging.config.LoggingReactiveAutoConfig;
        import com.santander.darwin.logging.logger.web.FunctionalLogger;
    
        @Configuration(proxyBeanMethods = false)
        public class ReactiveLoggingConfig {
    
            @Bean
            public ReactiveFunctionalLogger functionalLogger() {
                return new CustomFunctionalLoggerImpl();
            }
        }

### How to enable Tomcat/Catalina traces

Apache Tomcat uses JUL (java.util.logging framework) to manage its internal traces. In order for the Log4j2 implementation to be able to process and display on the console all the traces coming from JUL, you have to make use of the JDK's Log4j
logging adapter. This provides a custom implementation of the `java.util.logging.LogManager` class that makes use of Log4j2.

To enable this feature, set the `java.util.logging.manager` system property to [org.apache.logging.log4j.jul.LogManager](https://logging.apache.org/log4j/log4j-2.2/log4j-jul/apidocs/org/apache/logging/log4j/jul/LogManager.html). For this, the call
to `System.setProperty(…​)` in the main method of the application should be used. Alternatively, this could be done via the command line, by adding the argument `-Djava.util.logging.manager=org.apache.logging.log4j.jul.LogManager` in the run
statement of the application.

For example, if you wanted to enable tomcat/catalina traces in a `servlet` microservice, the application's main method would look like this:

    import org.springframework.boot.WebApplicationType;
    import org.springframework.boot.autoconfigure.SpringBootApplication;
    import org.springframework.boot.builder.SpringApplicationBuilder;

    @SpringBootApplication
    public class Application {

        public static void main(String[] args) {

            System.setProperty("java.util.logging.manager", "org.apache.logging.log4j.jul.LogManager");

            new SpringApplicationBuilder(Application.class)
                    .web(WebApplicationType.SERVLET)
                    .run(args);
        }
    }

In the properties file, you should set the required log level for each of the tomcat or catalina packages you want to trace. In this case, the `DEBUG` level is set for the catalina and tomcat packages:

    logging.level:
      org.apache.catalina: DEBUG
      org.apache.tomcat: DEBUG

!!! note

    For more information on the Log4j2 adapter for JDK logging, see [documentation](https://logging.apache.org/log4j/log4j-2.2/log4j-jul/apidocs/index.html).

### How to customize ObjectMapper

It is possible to customize the ObjectMapper by adding the necessary modules or the serialization/deserialization configuration. To do this we would have to create the following bean in a microservice configuration file. This configuration will
apply to the functional and security helper logs.

Below is an example of how to add the JavaTimeModule module:

    @Bean
    public Jackson2ObjectMapperBuilder customObjectMapper() {
        return new Jackson2ObjectMapperBuilder() {
            @Override
            public void configure(ObjectMapper objectMapper) {
                super.configure(objectMapper);
                objectMapper.registerModule(new JavaTimeModule());
            }
        };
    }

You can also use method of ObjectMapper *setConfig* to customize serialization/deserialization.
