# Microservices development standards

The following is a list of rules that any microservice developed in *Gluon* should comply with:

## RUNTIME

- Microservices should preferably be developed in Java 17. For compatibility reasons, Java 11 development will be supported on a temporary basis.
- The images to be deployed in the different environments will always use java 17 as a base image. or compatibility reasons, Java 11 development will be supported on a temporary basis.

## APIs

- The API exposed by the microservices must be properly documented with open-api (swagger is deprecated).
The documentation on how to implement a microservice with open-api can be consulted in the following [Darwin Guide](https://github.com/santander-group-shared-assets/gln-back-darwin-java-samples/tree/develop/openapi-springdoc) or [Arsenal Guide](https://redesigned-dollop-j8gwrgp.pages.github.io/pages/how-to-guides/api/using-contract-first/).
- Microservice endpoints will have to comply with the recommended standards. The best practices can be found in the following [guide](https://santanderdigitalservices.developers.sandigital.corp/en/baas_governance/documentation/ef464f22-f9c3-4c46-a243-cc5ab22d6a6b?ocn=true).

## CODING

- Newly developed microservices will have to be implemented with the latest available version of the architecture.
- Microservices, as far as possible, should always be aligned with the latest version of the archetype, even if the microservice already exists and is not in the latest version of the architecture.
- Microservices must use the dependencies defined by the architecture (in its corresponding version). If you need a dependency that does not include Arsenal or Darwin, you should use, whenever possible, dependencies defined by spring or spring-boot.
- Microservices must generate and manage error messages according to [current standards](error-management.md).

## CONFIGURATION

- The configuration of the microservices must follow the rules published in the following [guide](microservice-configuration.md)

## OBSERVABILITY

- It will be mandatory for microservices to send their log traces to the logging platform and meet [Gluonlog 1.0 observability standard](https://miniature-chainsaw-5f0ec678.pages.github.io/pages/logging/gluonlog/).
- Microservices should incorporate Health Check mechanisms to be able to monitor their health status.

## RESILIENCE

- Microservices must be resilient by applying the patterns described in this [guide](resilience.md).
- All invocations to external services that make use of spring components named restTemplate/webClient must implement the CircuitBreaker and Timeout patterns. For implementation details see the following [document](https://github.alm.europe.cloudcenter.corp/sanes-darwin-poc/darwin-samples/tree/develop/resilience).
- Microservices must be configured to support graceful shutdown, so that when stopped, requests are allowed to terminate correctly and connections are properly closed.

## QUALITY

- Microservices should have unit and integration tests to verify that they behave as expected.
- Darwin microservices must pass the quality gates defined by sonar and, as far as possible, minimize the major ones as much as possible.

## DOCUMENTATION

- The microservices must have 'readmes' files in markdown (recommended) or asscidoc format that explain the functionality of the microservice (it is recommended to start from the documentation generated by the archetype).
They should also contain a 'changelog' file with the changes introduced in each of the releases.
