# Darwin Spring Boot Metrics ![5.8.2](https://img.shields.io/badge/5.8.2-FF073D)

![Current](https://img.shields.io/badge/CURRENT-30FF24) ![GA](https://img.shields.io/badge/GA-C81D11)

## Description

The `darwin-spring-boot-metrics` library allows to register and consume, through the Darwin metrics system, the different micrometer metrics that can be used in Darwin microservices.

- Metrics traces. These traces come in two flavours:

    - Automatic: The traces registered in micrometer are automatically sent to the DarwinMeterRegistry component of the metrics library.

    - Manual: These traces can be generated by using the `MetricsLogHelper` class.

!!! info "Important"

    Metrics library is only available to use with Spain observability infrastructure.

!!! tip "Darwin Logging dependency"

    For the proper work of this module, the `darwin-spring-boot-starter-logging-kafka` dependency has to be included 
    in the application in order to configure the Kafka host and the topics used for sending the traces.

## Functionality

The metrics library will autoconfigure all its functionalities for any `Spring Boot` application runtime environment, being those defined in
[WebApplicationType](https://docs.spring.io/spring-boot/docs/3.3.12/api/org/springframework/boot/WebApplicationType.html): NONE, SERVLET and REACTIVE.

Visit the [Darwin Flavours section](../../ABOUT.md#darwin-flavours)
to get more info about how to work the application type detection.

### Metric registry

This library provides a step metric registry or ***StepMeterRegistry*** configured for immediate use. This registry is in charge of receiving and publishing in configurable time intervals, the different metrics that have been linked to it.

Once this library has been imported, there is a bean of the *MeterRegistry* class that contains a register of the *GenericStepMeterRegistry* type. This class is prepared to register and publish the different types of Micrometer metrics. Among other
configurable parameters, the registry has a formatter and a consumer that will define the format of the metrics and their consumption after publication. We can also filter the metrics we want to publish by means of a whitelist.

!!! note

    For more information on the operation and details of Micrometer and its metrics, see its [documentation](https://micrometer.io/docs/concepts).

The register provided has a formatter and a consumer provided by the library, which will be detailed below. In addition, this log provides already configured *environment*, *appKey*, *paasProject*, *paasApp* and *serverId* variables (necessary for
the consumption of publications by the Darwin metrics system), whose values are taken from the [Logging](../darwin-spring-boot-logging/README.md) library.

Below is an [example](#metric-registry) of how to reuse this registry to define new metrics.

### Formatter

The library implements a formatter, using the *MessageFormatter* interface. This formatter will be in charge of providing in a JSON formatted for the Darwin Logging library the different published metrics, being these later consumed in this format.

The library has an implementation of this interface, through the *DarwinMessageFormatter* class, which is available through a bean and by default is used in the provided log. This formatter **only implements the formatting of the following metrics**
(the resulting format is shown next to them):

- **Gauge**:

<!-- -->

    {"extensionType":"metrics","environment":"test","appKey":"darwin","paasProject":"darwinTest", "paasApp":"darwinApp","serverId":"localHost","region":"localRegion","timeStamp":"2019-11-20T17:02:40.251Z","name":"mytest","_tags":{"tag1":"test1"},"metricType":"Gauge","value":2.0}

- **Timer**:

<!-- -->

    {"extensionType":"metrics","environment":"test","appKey":"darwin","paasProject":"darwinTest", "paasApp":"darwinApp","serverId":"localHost","region":"localRegion","timeStamp":"2019-11-20T17:02:40.277Z","name":"mytest","_tags":{"tag1":"test1"},"metricType":"Timer","count":1,"total":4.5792E9,"max":4.5792E9}

- **Counter**:

<!-- -->

    {"extensionType":"metrics","environment":"test","appKey":"darwin","paasProject":"darwinTest", "paasApp":"darwinApp","serverId":"localHost","region":"localRegion","timeStamp":"2019-11-20T17:02:40.052Z","name":"mytest","_tags":{"tag1":"test1"},"metricType":"Counter","value":2.0}

- **FunctionCounter**:

<!-- -->

    {"extensionType":"metrics","environment":"test","appKey":"darwin","paasProject":"darwinTest", "paasApp":"darwinApp","serverId":"localHost","region":"localRegion","timeStamp":"2019-11-20T17:02:40.052Z","name":"mytest","_tags":{"tag1":"test1"},"metricType":"FunctionCounter","value":2.0}

In all of them the *\_tags* field may contain any number of entries, depending on each metric.

!!! info "Important"

    Pay special attention that the *DarwinMessageFormatter* only implements the format for three of the eight Micrometer metrics. If you want to use this formatter with any library that uses metrics other than those listed above,
    you will have to implement the formatting methods for those metrics by extending the provided bean. An [example](#formatter) of how to do this is shown below.

### Consumer

The metrics registry uses a consumer, which implements the *DarwinRegistryConsumer* interface. The function of this consumer is to collect the already formatted metrics and process them or send them to where you want to process them.

By default, the *DarwinRegistryConsumerImpl* consumer is provided by a *bean* in the Spring context. This consumer will collect the formatted metrics and send them to the Kafka topic of metrics, configured by default in Darwin microservices via the
`darwin.logging.kafka.topic.metric` property. This consumer uses the *MetricsLogHelper*, documented in the [Logging](../darwin-spring-boot-logging/README.md) library to plot these metrics.

### Manual metrics traces

- The `MetricsLogHelper` class is provided giving projects the possibility to generate metrics traces.

## Installation and configuration

To add the library to any project you will need to include the maven dependency in the project:

    <dependency>
            <groupId>com.santander.darwin</groupId>
            <artifactId>darwin-spring-boot-starter-metrics</artifactId>
    </dependency>

!!! info "Important"

    The metrics library requires the logging library, therefore its use implies the implicit incorporation of the `darwin-spring-boot-logging` library.

### Configuration

The metrics library has three main configurable properties:

<!tag:properties>

| Name                                   | Default value                                         | Required | Description                                        | Supported values                                                   |
|----------------------------------------|-------------------------------------------------------|----------|----------------------------------------------------|--------------------------------------------------------------------|
| darwin.logging.metric.step             | PT60S                                                 | No       | Time interval between metrics releases             | String (must be in ISO-8601 duration format: `PnDTnHnMn.nS`)       |
| darwin.logging.metric.enabled          | true                                                  | No       | The registry publishes metrics when true           | String (true or false)                                             |
| darwin.logging.metric.meter-white-list | <ul><li>darwin.**</li><li>resilience4j.**</li></ul>   | No       | List of packages whose metrics you want to publish | List (with packages to be published in String format with AntPath) |

<!end:properties>

!!! info "Important"

    Keeping the default value of the `meter-white-list` property automatically enables the use of Resilience4j metrics.

!!! note

    Due to the complexity of the data type of some properties, [examples](#library-configuration) are included below to configure them.

### Log4j2 configuration in XML format

The metrics library, through the use of the logging module's traceability context customisation API, adds to the configuration the metrics module's own components.
By default, the library adds to the [logging base configuration](../darwin-spring-boot-logging/README.md#log4j2-configuration-in-xml-format) a Logger and an Appender Kafka from the metrics library.
These components are represented in the XML below:

    <?xml version='1.0' encoding='UTF-8'?>
    <Configuration name="DARWIN_CONFIG">

        <!-- Appenders -->
        <Appenders>
            <!-- Kafka Appender -->
            <Kafka name="KAFKA_METRICS"  topic="nuar-metrics-log">
                <PatternLayout pattern="%m" />
                <Property name="bootstrap.servers">kafkadarwin.santander.dev.corp:9092</Property>
                <Property name="request.timeout.ms">2000</Property>
                <Property name="acks">0</Property>
                <Property name="batch.size">1048576</Property>
                <Property name="linger.ms">5</Property>
                <Property name="security.protocol">SSL</Property>
            </Kafka>
        </Appenders>

        <!-- Loggers -->
        <Loggers>
            <AsyncLogger name="MetricsLog" level="INFO" additivity="false">
                <AppenderRef ref="CONSOLE_TECHNICAL"/>
                <AppenderRef ref="KAFKA_METRICS"/>
            </AsyncLogger>
        </Loggers>
    </Configuration>

## Native compilation support

This module is not compatible with the native compilation.

## Exposed API

| Name                       | Type                   | Description                                                                                                                       | Application Type      |
|----------------------------|------------------------|-----------------------------------------------------------------------------------------------------------------------------------|-----------------------|
| GenericStepMeterRegistry   | MeterRegistry          | Metrics logging bean that publishes at configurable time intervals                                                                | <ul><li>All</li></ul> |
| DarwinMessageFormatter     | MessageFormatter       | Formatter bean that will collect Gauge, Counter and Timer metrics and return them in JSON format.                                 | <ul><li>All</li></ul> |
| DarwinRegistryConsumerImpl | DarwinRegistryConsumer | Consumer bean in charge of sending the metrics, already formatted, to the Kafka metrics topic                                     | <ul><li>All</li></ul> |
| MetricsLogHelper           | Utility class          | Auxiliary class that facilitates the writing of metrics logs, it has a single static method that receives the trace to be written | <ul><li>All</li></ul> |

## Use cases

### Library configuration

#### White list

The white list uses AntPath to *match* the different packages to be included, using the dot `"."` as a separator. Therefore, if we want to include Darwin's package metrics, we must include in the whitelist: `darwin.**`. For more information about
this format see the following [link](https://docs.spring.io/spring-framework/docs/6.1.20/javadoc-api/org/springframework/util/AntPathMatcher.html).

By default, the white list includes metrics from `darwin`, `resilience4j`, as shown in the following *yml*:

    #DEFAULT VALUES
    darwin.logging.metric:
        meter-white-list:
            - darwin.**
            - resilience4j.**           

To change the value of this, simply set the `darwin.logging.metric.meter-white-list` property to the desired packages.

An example of a custom white list configuration can be seen below:

    darwin.logging.metric:
        meter-white-list:
            - darwin.**.metrics
            - resilience4j.*.state
            - test.*.metrics.**

#### Time interval

To define the time interval in which the metric logging publishes these metrics, the `darwin.logging.metric.step` property must be configured. This shall be in the format `PnDTnHnMn.nS`, where ***n*** represents the number of:

- Days: `nd`

- Hours: <strong>n</strong>H

- Minutes: <strong>n</strong>M

- Seconds (may have decimals): <strong>n.n</strong>S

In this format, characters preceded by an **n** are not required if the **n** does not take a value. For example:

- P**2D**T**3H10M5.638S**: Represents 2 days, 3 hours, 10 minutes and 5.638 seconds.

- PT**3H0.005S**: Represents 3 hours and 5 milliseconds.

### Metrics logger customization

The library automatically creates and configures a metrics logger that is added to the logging context. In addition, in case a route has been defined for the Kafka service, a Kafka appender will be created and added for sending metrics to the Darwin
observability system.

This default configuration will be valid for most `Darwin` projects, but it could be the case of wanting to customise it for certain environments or even rewrite it completely based on the requirements of a project or entity, therefore, the metrics
module has been provided with the necessary functionalities to be able to customise and implement any requirement. In order to carry out this task, the logging module exposes the functional interface,
[LoggingConfigCustomizer](https://gluon.dev.corp/microservices/docs/darwin-spring-boot/5.8.2/apidocs/com/santander/darwin/logging/LoggingConfigCustomizer.html), which allows certain modifications to be made
on the logging components through the interface [LoggingConfig.Builder](https://gluon.dev.corp/microservices/docs/darwin-spring-boot/5.8.2/apidocs/com/santander/darwin/logging/LoggingConfig.Builder.html).
If we add to this the use of Spring's [*@Profile*](https://docs.spring.io/spring-framework/docs/6.1.20/javadoc-api/org/springframework/context/annotation/Profile.html) annotation, we will be able to create different configurations of the metrics log
per environment.

For example, as we have mentioned, the metrics module automatically creates an appender to send metrics to Kafka but, how could we customise the metrics module to add to the metrics logger a new appender that allows to show the metrics by console
and only in test environments? Making use of the customizers in the logging library would be as simple as:

    import org.apache.logging.log4j.core.appender.ConsoleAppender;
    import org.apache.logging.log4j.core.config.builder.api.AppenderComponentBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilder;
    import org.apache.logging.log4j.core.config.builder.api.ConfigurationBuilderFactory;

    import static com.santander.darwin.metrics.config.MetricProperties.METRICS_LOG;
    import static com.santander.darwin.metrics.config.MetricProperties.CONSOLE_METRICS;

    @Configuration(proxyBeanMethods = false)
    class MetricsCustomConfiguration {

        @Bean
        @Profile("test")
        LoggingConfigCustomizer metricsLoggingConfigCustomizer() {
            return (LoggingConfig.Builder builder) -> {

                ConfigurationBuilder<BuiltConfiguration> configBuilder = ConfigurationBuilderFactory.newConfigurationBuilder();

                AppenderComponentBuilder metricsConsoleAppender = configBuilder.newAppender(CONSOLE_METRICS, "CONSOLE")
                                                                                .addAttribute("TARGET", ConsoleAppender.Target.SYSTEM_OUT)
                                                                                .add(configBuilder.newLayout("PATTERN_LAYOUT")
                                                                                            .addAttribute("PATTERN", "%d{HH:mm:ss,SSS}"));

                builder.addAppender(metricsConsoleAppender)
                        .addRefAppenderLogger(METRICS_LOG, CONSOLE_METRICS);
            };
        }
    }

In this example a console appender is being created with a custom pattern, it is added to the configuration, and a reference is created between the metrics log and that appender. This customisation will only apply when the application is running in
an environment where the profile is equal to *'test'*.

For more information on how to customise the logging components, see the [documentation](../darwin-spring-boot-logging/README.md) of the logging module.

!!! info "Important"

    The metrics logger name is accessible through the `METRICS_LOG` constant defined in the *MetricProperties* class. In order to use it, you simply have to do a static import.

        import static com.santander.darwin.metrics.config.MetricProperties.METRICS_LOG;

### Extending library components

It is possible to extend the functionality of the library by reusing the components it exposes.

#### Metrics registry

To reuse the default darwin metrics log, we need to inject a bean of the following type:

    @Autowired
    MeterRegistry registroDarwin;

Once we have the registry, we can use it to create our own Micrometer metrics, linking them to the *registry* we just injected.

Another option is to use the registry to publish metrics from libraries integrated with micrometer, as in the case of Resilience4j, shown below

    @Autowired
    CircuitBreakerRegistry circuitBreakerRegistry;

    TaggedCircuitBreakerMetrics
            .ofCircuitBreakerRegistry(circuitBreakerRegistry)
            .bindTo(registroDarwin);

#### Formatter

In case you want to reuse the provided formatter in your own implementation, you should inject it as follows:

    @Autowired
    @DarwinQualifier
    MessageFormatter darwinMessageFormatter;

The MessageFormatter interface has a *format* method for each of the Micrometer metrics, which will collect the different metrics published by the registry and return them in the desired format:

    T format(Gauge meter);

    T format(Counter meter);
    (...)

By overwriting these methods we can extend the functionality of the formatter for each metric.

!!! tip "Caution"

    The sending and processing of metrics in the Logging architecture is strongly linked to the structure of the metrics, so it is recommended to **NOT** overwrite the implementation for existing metrics.

#### Consumer

To reuse the provided consumer in your own implementation you would have to inject it in the following way:

    @Autowired
    @DarwinQualifier
    DarwinRegistryConsumer darwinRegistryConsumer;

Note that by reusing the consumer, it will automatically send all the metrics from the libraries integrated with *Micrometer*, which are in the white list of metrics, to the configured Kafka topic. libraries integrated with *Micrometer*, which are
in the white list of metrics, to the configured Kafka topic. If you want to implement another consumer, you will have to replace it as explained in the following section.

### How to generate metrics traces manually

To generate metrics traces manually, the `MetricsLogHelper` class must be used, which generates the raw trace from the input data.

An example of the use of this class would be the following:

    String message = "Metrics logs test";
    MetricsLogHelper.log(message);

Which would produce the following trace:

    "Metrics logs test"

### Substitute library components

The Darwin Metrics Library allows you to substitute any of its components. In case you want to use a different register, formatter or consumer, you can simply create a bean of the following types with the custom components:

- **Registry:** To replace it you must create a bean that returns a custom registry of type `io.micrometer.core.instrument.MeterRegistry`.

- **Formatter:** To replace it, a bean must be created that returns a custom formatter of type `com.santander.darwin.metrics.formatter.MessageFormatter`, so the new formatter must implement that formatter. the new formatter must implement such an
    interface.

- **Consumer** : To replace it a bean must be created that returns a custom consumer of type `com.santander.darwin.metrics.consumer.DarwinRegistryConsumer`, again the consumer must implement that interface.

### Integration with Resilience4j

By default, the metrics library has an integration with *Resilience4j*, whereby all instances of the *resilience4j-spring-boot3* products (CircuitBreaker, Retry, BulkHead and RateLimiter) will register their metrics automatically. of
*resilience4j-spring-boot3* (CircuitBreaker, Retry, BulkHead and RateLimiter) will automatically register their metrics in the registry provided by the library. provided by the library. If you create a microservice with the Darwin archetype, using
this library, you will be directly registering the metrics of the Circuit Breaker and Retry metrics implemented in the [authentication](../darwin-spring-boot-security-authentication/README.md) and
[authorization](../darwin-spring-boot-security-authorization/README.md) libraries, whenever they are used.

These metrics are enabled by default. If you do not want to use these metrics, you can simply customise the white list without adding these packages, so that the registry would not publish them.

Likewise, if you want to use the *Resilience4j* products without using the *resilience4j-spring-boot3* annotations, you must proceed as follows:

- Inject the product registration *bean* (CircuitBreaker, Retry, BulkHead or RateLimiter):

<!-- -->

    @Autowired
    CircuitBreakerRegistry circuitBreakerRegistry;

- Create the instance in this registry:

<!-- -->

    CircuitBreaker circuitBreaker = circuitBreakerRegistry.circuitBreaker("circuitBreakerInstance");

- For Retry, Bulkhead and RateLimiter you should proceed in the same way.

Note that even if you do not use the products via the Spring annotation, you need to depend on *resilience4j-spring-boot3* if you want the integration to be automatic. If you want the integration to be automatic. If you want to use the
*Resilience4j* products, and you are not using the *resilience4j* authentication or authorisation libraries, you will need the authentication or authorisation libraries, you need to import the *resilience4j-spring-boot3* dependency:

     <dependency>
        <groupId>io.github.resilience4j</groupId>
        <artifactId>resilience4j-spring-boot3</artifactId>
     </dependency>

!!! note

    For more information on the use of *Resilience4j*, please refer to the [Darwin Circuit Breaker](https://sanes.atlassian.net/wiki/spaces/SANACLOUD/pages/16524089013/Resilience+microservices) guide or to the documentation in
    [Resilience4j](https://resilience4j.readme.io/docs).
